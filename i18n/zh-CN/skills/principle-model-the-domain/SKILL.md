# 为领域建模

把真实领域编码进数据结构，而不是把它散落在条件分支里。与领域匹配的结构让非法状态无法表示，还能删掉分支。写代码的时候选对结构很便宜；事后再找回它，看起来就像一场重构，于是被无限推迟。

可以伸手去拿的有：

- 状态机，替代散落的布尔值、阶段标记或生命周期检查。
- 类型化模型，替代松散的参数或反复出现的形状假设。
- map、注册表、查找表或可判别联合，替代摊在多个文件里的分支。
- reducer 或命令/事件模型，替代临时的状态修改。
- 围绕一整块领域知识组织的模块，替代按「加载、校验、转换、保存」这种顺序排列的模块。执行顺序不是所有权。
- 把重复行为、所有权或不变量收拢到一起的小模块边界。
- 队列、缓存、索引、图、树或规范化集合——访问模式要什么就用什么。
- 任何其他合身的结构。都不合身时，先想清楚代码绝不允许什么、数据会被怎么读，然后找到恰好编码了这些的那个结构。

不要硬造抽象。如果当前的形状已经清晰、局部、不太可能长大，无聊的代码更好。对那种只加间接层、却消不掉分支、重复规则、非法状态或生命周期风险的抽象保持怀疑。

你跳过这条原则的标志是：一个新功能只是给已有的 if/else 链又加了一个分支，或者出现了第二个必须与第一个保持同步的布尔值。按时间阶段拆分模块也是一个标志——以阶段命名的模块会在各个步骤间重复同样的领域规则。
