# TDD 修 Bug

修复一个测试路径清晰且低成本的 bug 时，在改动生产代码之前，先把坏掉的行为变成可执行的。目标是一个聚焦的回归测试：修复前失败，修复后通过。

不切实际时不要硬造测试。如果可用的测试需要搭建大范围的测试设施、脆弱的 mock、缓慢的端到端基础设施、只有生产环境才有的状态、模糊的复现步骤，或大量无关的 fixture 改动，就跳过新增测试，改用最接近的有用验证手段。

## 工作流程

1. **理解 bug。** 弄清预期行为、当前行为、受影响的路径，以及可观察到的最小复现。
2. **选择最窄的可执行检查。** 优先选用该代码路径已经在用的、最接近的单元、组件、集成或回归测试。如果没有明显可行的测试路径，不要为了满足流程而凭空造一个。
3. **先写失败测试。** 加上能抓住这个 bug 的最小聚焦测试。测试应当编码预期行为，而不是照抄当前实现。
4. **修复前先跑新测试。** 确认它因为预期的原因失败。如果它通过了，或因无关原因失败，先修正测试或复现，再动实现。
5. **修复 bug。** 用满足预期行为的最小生产改动来修，同时保持邻近的约定不变。
6. **重跑回归测试。** 确认测试现在通过。

## 当失败测试不切实际时

改用最接近的可执行回归检查：定向脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不加新测试，也不要坏测试。坏测试是指：主要在测 mock、编码了当前实现细节、依赖时序或无关全局状态、为一个小修复需要昂贵基础设施，或证明修复后会立刻被删掉的测试。

## 护栏

- 不要为了迁就错误的实现而改测试。
- 不要弱化现有断言，除非预期行为确实变了且理由清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围 fixture 改动或无关的覆盖率扩张。
- 如果 bug 是偶发的，尽量让测试具有确定性，并记录下所锁定的信号。
- 如果这个 bug 暴露了更大一类失败，先落地聚焦的回归路径，再考虑补充相邻的兄弟覆盖。

## 最终回复

报告证据，而不只是结论：

- 点名修复前失败的测试或可执行检查，以及它产生的失败。
- 点名修复后通过的测试运行，以及做过的邻近验证。
- 如果无法展示修复前失败的证据，说明原因，并描述实际使用的最接近的回归检查。
