# 类型系统纪律

让编译器拒绝不可能的状态、不匹配的基元和未处理的分支。优先通过定义让错误和特例不存在，而不是繁殖一堆处理器。TypeScript 语法层面的内容见 `typescript-best-practices` 技能。

- **让非法状态无法表示。** 把变体建模为和类型（可判别联合、带负载的枚举、密封类），而不是一袋可选字段——矛盾的组合在那里照样能编译。`{ completed: boolean; completedAt?: Date }` 允许 `completed: true` 却没有日期。从 `completedAt` 推导出这个布尔值，或者建模为 `{ kind: 'open' } | { kind: 'done'; at: Date }`。如果你能写一段注释解释哪种字段组合是合法的，那就该把它拆成和类型。
- **类型是构造，不是限制。** 从你想要的值出发把类型搭起来，而不是从一个更松的类型里靠检查把它切出来。非空列表就是一个头加一个尾。合法的时间范围就是一个起点加一个时长。选那个根本构造不出非法值的形状，再在上面暴露调用方需要的接口。
- **给语义基元打品牌。** `UserId` 和 `OrderId` 底层都是字符串，但不该能互换。各给各的类型，比如 TypeScript 里的品牌交叉类型，或者别处的 newtype。创建时校验一次，下游信任类型。两个参数共享同一个基元类型但含义不同，就打品牌。
- **外部数据在解析之前没有类型。** RPC 负载、JSON、IPC 消息、CLI 参数、配置文件、环境变量、数据库行。在每个边界放一个解析函数，把非结构化输入变成类型化模型。**boundary-discipline** 原则技能讲了该把校验放在哪里。
- **别对类型系统撒谎。** 绕过编译器的强转、不安全强 coercion 和断言函数，都是潜伏的运行时崩溃。编译器证明不了的事实，要么你自己证明（校验、收窄、改进模型），要么承认这个强转就是个隐患。把每一个 `any`、`as` 或 `assertNotNull` 追到边界，在那里校验。
- **穷尽匹配是编译器的活。** 对和类型的匹配，必须在新增变体却没处理时编译失败，这样编译器会告诉下一个代理该在哪里加分支。用你语言的惯用法：TypeScript 里一个 `never` 类型的绑定，Rust 里不带注解的 `match`，Haskell 的 `-Wincomplete-patterns`，Kotlin 的密封类穷尽匹配。
- **从权威 schema 推导类型。** 当 protocol buffer、OpenAPI 规范、GraphQL schema、数据库迁移、design-token 文件或别的文件拥有一个形状时，从它推导，而不是手工搓一个平行类型。见 **encode-lessons-in-structure** 原则技能。
- **只在出现部分性的地方加强类型。** 一个运行时断言、null 检查或「这绝不该发生」的 throw，标记的就是类型太弱的地方。把那个检查推上去，推进类型里。然后停手。类型系统的职责是追踪每个使用点必须处理的情况，而不是尽可能精确地描述数据。优先全函数。空列表的 `sum` 是 0，所以它接受普通列表。空列表的 `head` 没有答案，所以它要求非空列表。如果没有东西会 panic，就保留普通类型。
