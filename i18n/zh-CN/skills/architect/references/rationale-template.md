# 设计理由模板

随类型草图一同交付的文字。一页篇幅。标题用句式大小写，不要八股套话。把斜体提示替换成实际内容。

## 问题

*一段话。我们要做什么，以及现有系统或约束中的什么让这个形状并非显而易见。如果 [阶段 A](../SKILL.md#phase-a-ground-the-problem) 浮出了设计必须遵守的约束（需要互操作的现有类型、不能打碎的调用方、越过我们边界的不变量），在这里点名它们，让读者看到你当时看到的同一批约束。*

## 用法（调用方视角）

*先写这一节，早于类型草图。展示使用者会读到的 README 或快速上手，外加他们自己代码里的两三个真实调用点：他们导入什么、调用什么、拿回什么。[形态](#shape) 中的类型草图由此派生。两者必须一致。发生分歧时，让草图向用法对齐，而不是反过来。调用方的体验就是规格说明，类型为它服务。*

## 形态

*推荐的架构。数据结构优先。然后是数据如何流经各个签名。点名承重的决策。说明哪些不变量被编码进了类型、校验放在哪里、系统刻意不做什么。明确评判接口深度。说明公共表面隐藏了什么复杂性、还有什么暴露给调用方、以及为什么接口不比所需要的大。为每个决策引用背后的原则（例如 `per boundary-discipline`）。不要复述原则内容。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成了基底及原因、从其余每个候选各嫁接了什么、以及否决了什么及原因。*

## 已接受的权衡

*所选形状做出的每个权衡一条要点。格式："我们接受 X，换取 Y。"点名任何未来读者可能误以为是疏漏的东西，包括那些看起来像过早优化或过早简化的东西。*

## 考虑过的备选方案

*必填。至少点名一个具体的备选形状，并用一行说明它为什么落选。按接口深度评判每个备选，而不是只看实现简单。点名它暴露给调用方的复杂性，和它隐藏的复杂性。当设计空间里真有竞争者时，这里应该有两三个备选。当约束逼出了唯一答案时，一个也可以，结论写成"这是唯一可行的形状，因为……"。避免列出同一个形状的各种口味。本节覆盖的是所选形状考虑过并否决的设计备选，而不是其他 runner 候选。*

## 待决问题与风险

*画草图期间注意到的、需要人类拍板的事，以及实现开始前值得标记的风险。用问句而不是断言来表述，这样人类的回答就是裁决，而不是一条评论。*

## 下一个实现步骤

*照着草图要构建的第一样东西。一句话。综合之后（或阶段 D 签字之后，如果选择了启用检查点）你会立刻开始写的东西。*
