# Architect runner 提示词

编排者在阶段 B 期间把本文件原样传给每个并行候选 runner，并在其周围填入变量输入：任务、阶段 A 的摸底产物、隔离的工作目录，以及输出写入路径。工作目录在可用时是 git worktree，否则是草图目录下每个 runner 一个的子目录。重要的是候选之间相互独立。

你正在为 architect 的并行探索产出一个候选设计。先完整通读 **architect** 技能，那就是你身处其中的工作流。输出一个候选设计包：类型草图、函数签名、模块地图，以及按 [`rationale-template.md`](rationale-template.md) 组织的文字设计理由。

应用以下纪律。编排者按这些维度比较各候选，以挑选基底。

- 调用方用法优先。先写 README 风格的用法和两三个真实调用点，再写类型，然后从中推导出类型草图。用法就是规格说明。两者必须一致，所以让草图向用法对齐，而不是反过来。
- 数据结构优先。把核心类型搞对，代码就显而易见了。把每个主导访问模式在提议的结构里走一遍。如果答案是"以后再加个映射表 / 索引 / 缓存"，那这个结构就是错的。
- 接口深度。比较隐藏在公共表面背后的能力相对于这个表面本身的大小。优先选择把复杂性拉进被调方的简单接口，哪怕实现因此变得不那么简单。不要把传输层或线路类型放上公共 API。在接口背后解析成领域类型。
- 共享状态：如果两个参与者都可能写入，问一句"会怎样？"如果答案不是"什么都不会发生"，默认按 **separate-before-serializing-shared-state** 原则技能，采用每参与者各自持有状态、在读边界合并的方案。
- 让边界可见。函数体用 `not implemented` 错误，棘手逻辑用 `// TODO` 伪代码，文档注释写明意图和不变量。读者应该只读类型和签名，就能把数据从输入追到输出。
- 把不变量编码进类型：难以误用的类型 > 运行时检查 > 文字注释，遵循 **encode-lessons-in-structure** 原则技能。
- 在边界校验，在内部信任类型，遵循 **boundary-discipline** 原则技能。业务逻辑写成纯函数。外壳保持单薄。
- 每条不变量只有一个权威来源。要派生，不要同步。
- 适用处做幂等的状态转移，遵循 **make-operations-idempotent** 原则技能。问一问：操作跑两遍、或中途崩溃，会怎样。
- 短调用链。如果追一遍流程需要超过三个文件，就把层级压平，遵循 **laziness-protocol** 和 **minimize-reader-load** 原则技能。

你是并行 runner 之一，各自运行在不同的模型上。产出你的模型能做出的最好设计。不要为防备其他候选而畏手畏脚。候选之间的差异正是用来挑选基底和做嫁接的信号。收敛到一个看起来安全的中间地带，就违背了探索的意义。
