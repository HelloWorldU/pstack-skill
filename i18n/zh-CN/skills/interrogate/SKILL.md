# Interrogate

为每个配置好的模型各派生一名评审者，对代码变更做对抗性评审。对抗性信号来自模型多样性，而不是分配的人设。交付物是一份综合裁断。不要自动应用变更。

## 第 1 步：范围

从上下文中确定要评审什么：

- 如果用户指向特定文件或某个 diff，就用它。
- 如果在功能分支上，运行 `git diff main...HEAD`（或合适的基准分支）拿到完整变更集。
- 如果用户的消息提到了最近的工作，收集相关文件。

把 diff 或文件内容打包，并附上评审者理解代码所需的任何周边上下文文件。

## 第 2 步：意图

在派生评审者之前，用一段清晰的话陈述意图，依据来自用户的消息、提交信息、PR 描述（如果有）以及代码。如果你对意图拿不准，先问用户再继续。

## 第 3 步：派生评审者

用 Task 工具在一条消息中启动所有评审者：`~/.cursor/rules/pstack-models.mdc` 里 `interrogate reviewers` 那一行有几个条目就派几个，依次标记为评审者 A、B……与条目数量对应。如果该规则或那一行缺失，使用下表的默认值。

| 子代理 | 默认模型 |
|----------|---------------|
| 评审者 A | `claude-opus-5-5-xhigh` |
| 评审者 B | `grok-4.7-xhigh-fast` |

每个评审者都带上 `subagent_type: generalPurpose`、`readonly: true`，`model` 设为它配置条目里的值；没有配置行时用它的表格默认值。对于 `auto` 或 `inherit-parent` 条目则省略 `model`，让该评审者运行在父级模型上。

如果 Task 工具拒绝了某个配置条目，就用该条目所属家族的表格默认值来运行这个评审者，并说明这一点。家族按前缀划分：`claude-*`，以及 `grok-*`、`cursor-grok-*` 和 `composer-*`。被拒的 `composer-*` 条目用评审者 B 的默认值运行。没有任何家族匹配时，用评审者 A 的默认值。如果连表格默认值也被拒绝，就从错误信息里列出的有效 slug 中选最接近的等价项来派生（优先同一家族、同一推理档位），并单独开一个 PR 更新默认表。不要因为 slug 问题阻塞评审。永远不要把别名条目当作被拒的 slug，也不要对它应用任何一种回退。

阅读 `references/reviewer-prompt.md`，为每个评审者填写同一个模板：已陈述的意图、diff 或文件内容、来自 `references/rubric.md` 的评审清单，以及来自 `references/code-quality-review.md` 的代码质量视角。按照 **poteto-mode** 技能的「子代理」一节，为每个子代理挑选适合这项任务的推理级别和快速/标准速度。

## 第 4 步：综合

随着结果陆续返回，构建统一的图景。解析每个评审者的发现。把以不同措辞描述同一问题的发现合并，并记下每条发现分别由哪些模型提出。两个或更多模型各自独立提出的发现是最高信号。只有一个模型提出的发现也要读，但按此相应调低权重。记录分歧。如果一个模型标记了某一点，而另一个明确给出相反结论，这就是裁断时要考虑的上下文。

## 第 5 步：首席判断

你是首席评审者，一名务实的高级工程师，不是中立的聚合器。完整框架见 `references/lead-judgment.md`。把每条发现放进四个桶之一，附上提出它的模型和一行理由。

- **处理（Act on）**。结合真实目标来看，确实影响正确性、安全性或可维护性的问题。它们会挡住一个真实的 PR。
- **考虑（Consider）**。成立，但你不确定现在处理它们的收益是否盖过成本。值得用户关注。
- **记下（Noted）**。技术上成立但不可行动。依赖上下文、属于过早优化，或在此阶段影响很小。
- **驳回（Dismissed）**。错误、吹毛求疵，或缺少上下文，附简短理由。

## 输出格式

### 意图
> [第 2 步中陈述的意图段落]

### 评审者
- 评审者 [标签]：[模型名称]，[N 条发现]（每个评审者一条）

### 处理
[每条：描述、由哪些模型提出、为什么重要。]

### 考虑
[每条：描述、由哪些模型提出、权衡所在。]

### 记下
[简要列表。]

### 驳回
[每条附简短理由。]

### 一致性地图
[模型们在哪些地方一致、在哪里分歧，以及这种模式说明了什么。]
