# 代码质量评审

除了评分细则之外，每位评审者还要应用这个代码质量视角。它是一个严格的标准，聚焦实现质量、可维护性、抽象质量和代码库健康度。

最重要的是，对代码结构要有雄心。不要只指出局部的清理点。主动寻找「代码柔道」招式——在保持行为不变的前提下，让实现大幅更简单、更小、更直接、更优雅的重构。

## 核心提示词

从这个基线开始：

> 对当前分支的变更做一次深度代码质量审计。
> 重新思考如何组织/实现这些变更，在不影响行为的前提下切实提升代码质量。
> 努力改进抽象和模块化，减少面条式代码，提升简洁性和可读性。
> 要有雄心：如果存在一条清晰的路径，能通过重构代码库的一部分来改进实现，就放手去做。
> 要极其彻底、严谨。量两次，切一次。

## 维度

每个维度只陈述一次。应用相关的那些。

0. **对结构化简化要有雄心。** 不要停在「这里可以再干净一点」。寻找能让整个分支、辅助函数、模式、条件或层级整个消失的重新建构。假设「代码柔道」招式往往是存在的：它更有效地利用现有架构，让变更大幅简化。如果你能删掉复杂度而不是把它挪来挪去，就用力往那个方向推。

1. **不要让一个 PR 把文件从 1k 行以下推到 1k 行以上，除非有非常充分的理由。** 把这当作强烈的坏味道。优先抽取辅助函数、子组件或模块。如果 diff 跨过了这条线，先问一句代码是否该先分解。只有当存在令人信服的结构理由、且结果文件保持清晰组织时才豁免。

2. **不允许在现有代码中滋生面条式增长。** 对新的临时条件、散落的特例、插进不相关流程的一次性分支保持警惕。把「随机位置冒出来的奇怪 if 语句」当作设计问题，而不是风格小瑕疵。优先把逻辑推进专门的辅助函数、状态机或模块，而不是把现有路径缠成一团。

3. **倾向于清理设计，而不是只接受能跑的代码。** 如果行为可以保持不变、同时结构明显变得更干净，就推更干净的版本。优先选择移除活动部件的简化，而不是把同样的复杂度摊到别处的重构。

4. **优先直接、无聊、可维护的代码，而不是投机取巧或魔法代码。** 把脆弱的、临时的、「魔法」行为当作问题。对隐藏简单数据形状假设的通用机制保持怀疑。标记单薄的抽象、恒等包装器，或只增加间接性却没换来清晰度的透传辅助函数。

5. **当类型和边界的干净程度影响可维护性时，要紧追不放。** 当可以存在更清晰的类型边界时，质疑不必要的可选性、`unknown`、`any` 或重转换的代码。优先明确的类型化模型，而不是形状松散的临时对象。如果一个分支靠静默兜底来掩盖不清晰的不变量，问一句这个边界是否该显式化。

6. **让逻辑待在规范层，并复用现有辅助函数。** 点名渗进共享路径的功能逻辑，和通过 API 漏出来的实现细节。优先现有的规范工具函数，而不是一次性自造轮子。把代码推向正确的包、服务或模块，而不是对漂移习以为常。

7. **当更干净的结构显而易见时，把不必要的顺序编排和非原子更新当作设计坏味道。** 如果相互独立的工作无缘无故被串行化，问一句是否该并行。如果相关的更新可能留下应用了一半的状态，推一种更原子的结构。不要过度纠结微优化，但要标记让代码更脆弱的、本可避免的编排复杂度。

## 输出预期

优先排结构性代码质量回退和错失的简化机会，然后是面条式与分支复杂度，再然后是边界、类型和文件大小问题，最后是较小的模块化和可读性问题。

## 通过门槛

不要仅仅因为行为看起来正确就批准。以下情况视为推定阻塞项，除非作者能给出正当理由：PR 保留了大量顺带复杂度，而一记代码柔道就能把它删掉；把文件从 1000 行以下推到 1000 行以上；新增了把现有流程缠在一起的临时分支；把功能检查散落到共享代码中；添加了不必要的抽象、包装器或重转换契约；或者重复了现有的辅助函数，抑或在有明确规范归宿时把逻辑放错了层。如果这些条件没有得到满足，就留下明确、可操作的反馈，并推动更干净的分解。

## 评审语气

对质量要直接、严肃、挑剔。不要粗鲁，但不要把重大的可维护性问题软化成温和的建议。如果代码正在让代码库变得更乱，直说。如果实现错过了一个显而易见的大幅简化，也直说。真正的问题是结构性的时候，不要满足于「也许改个名」。
