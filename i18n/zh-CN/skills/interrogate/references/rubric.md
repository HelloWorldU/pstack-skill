# 评审清单

通过所有相关的视角来评审。并非每个视角都适用于每一次变更。

## 正确性

代码是否真的做到了意图所声明的事情？

- 边界情况：空输入、nil/undefined、边界值、并发访问
- 错误处理：错误是被捕获、被传播，还是被静默吞掉？
- 差一错误（off-by-one）、类型强转、整数溢出、字符串编码
- 状态管理：竞态条件、过期闭包、悬垂引用
- 快乐路径和悲伤路径都走得通吗？
- 幂等性：如果这个操作执行两次，或者上一次执行中途崩溃，会发生什么？如果答案是「取决于留下了什么状态」，那就缺一个对账（reconciliation）步骤。
- 并发：如果多个参与者都能触碰同一份可变状态（文件、分支、共享数据），访问是结构性地串行化的（锁、顺序阶段、排他所有权），还是靠根本撑不住的约定？

当你发现一个潜在 bug 时，追踪它的执行路径。不要只标记「这可能是 nil」。给出让它变成 nil 的那条调用链。

## 根因 vs. 症状

代码是在修复真正的问题，还是在给症状打掩护？

回答这个问题往往需要看到被改文件之外的东西。阅读周边代码（调用方、被调方、类型定义、兄弟模块），理解这次变更所处的架构。用你手上的工具（Read、Grep、Glob）顺着调用链走，读类型定义，在判断这次变更是否打在正确的层面之前，先弄明白这段代码为什么存在。

- 掩盖了更深层不变量破坏的守卫子句
- 隐藏了被破坏契约的重试逻辑
- 压制了建模错误的类型强转
- 一处 workaround：为什么需要它？正确的修法长什么样？
- 在模块 A 里做的修复，其实应该修在模块 B 的契约上
- 本该用结构解决却用了指令的情况：如果这个修复是一条写着「不要做 X」的注释，或者一个必须靠人记住的约定，问问它能不能改成类型约束、lint 规则，或者一个让错误做法不可能发生的运行时检查

## 结构完整性

代码是否良好地融入了它所在的系统？

- 边界纪律：校验是放在系统边界上，还是散落在业务逻辑里？数据在进入系统的地方校验一次，然后在内部信任它。
- 抽象层次：代码是否把高层编排和底层细节混在一起？
- 耦合：这次变更是否引入了会让未来变更更困难的依赖？
- 数据模型契合度：数据结构是否匹配实际的访问模式？
- 外挂式 vs. 融入式：如果一开始就知道这个新需求，代码会长成现在这样吗？还是这次变更感觉像一块贴在现有设计上的补丁？
- 遗留双路径：这次变更是否引入了新 API，同时让旧 API 继续活着？如果没有外部消费者，就在同一波里迁移调用方并删除旧路径。不要留下会变成永久存在的兼容层。

不要因为代码简单而惩罚它缺乏抽象。过早抽象比重复更糟。

## 验证

光读代码，你能判断它确实有效吗？

- 有测试吗？它们测的是行为还是实现细节？
- 有没有能抓住回归的断言/不变量？
- 如果这是 bug 修复：有没有针对这个 bug 的测试？
- 如果触及集成边界：完整路径被测过了吗？
- 检查真实的东西，而不是代理指标。如果代码通过文件 mtime 或缓存状态来判断存活，而不是读取实际值，那就是一个验证缺口。
- 对于委派出去或异步完成的工作：代码验证的是实际产出物，还是轻信了自我报告和总结？

## 复杂度预算

复杂度是否被代码所完成的事情证明是合理的？

- 本可以更简单、且不损失正确性或清晰度的代码
- 只服务于一个调用点的抽象
- 为尚不存在的情况做的配置或参数化
- 死代码、未使用的导入、残留的参数
- 过度工程：没有任何当前调用方的「以防万一」代码路径
- 为不再需要的过渡稳定性而保留的过时兼容路径。如果迁移已经完成，就删掉脚手架
- 用户体验是否撑得起这份复杂度？每个功能、控件和选项都应该凭价值赢得自己的位置。半成品功能比没有更糟。

除非更简单是错的，否则更简单就是更好。

## 安全

对每个安全发现，追踪输入在代码中的流经路径，并把它展示出来。

- 用户输入未经净化就流入危险的汇聚点（SQL、shell、eval、innerHTML）
- 新端点上的认证/授权缺口
- 出现在代码、日志或错误消息中的密钥
- 安全关键路径上的 TOCTOU（检查时刻与使用时刻的时间差问题）
