# 写好提示词

提示词陈述意图和「完成」的判定标准。步骤由行动手册提供，所以几句大白话胜过一份规格说明书。

## 要写的

- 目标。说清楚哪里不对，或者用户想要什么。
- 完成判定。它必须能通过或不通过。「做得更好」和一个时长都不算判定标准。
- 要出示的证据。要求真实的命令输出、流程的视频、存下来的值，或前后对比的数字。
- 用户已经知道的东西。一个症状、一条复现步骤、一份日志或一个链接，能省掉代理一轮搜索。
- 真正的约束。「先复现」、「先别改任何代码」、「行为零变化」、「先让我评审再继续」，每一条都会改变代理的做事方式。

## 不写的

- 怎么做。说要达到什么，给代理留出找到更优解的空间。
- 技能或步骤的清单。手写的顺序会丢掉或打乱行动手册所保留的步骤。只有要推翻某个选择时才点名一个技能。
- 用户对原因的理论，至少在代理复述问题之前不要写。一个说出口的猜测会收窄搜索范围。

## 先加载上下文

- 对于嘈杂的报告，让代理在做任何其他事之前，用自己的话、用大白话复述底层问题。误读会在任何代码出现之前暴露。
- 在新聊天里，用 `/recall` 找回这个话题上早先的工作。旧聊天里存着新代理没有的上下文。
- 改动不熟悉的代码之前，用 `/how` 弄清机制，用 `/why` 弄清原因。脑子里没有追踪过模型的代理，会在第一个看似合理的地方修症状。
- 让 `/teach` 为一个选择做论证，比如「说服我它修的是根因而不是症状」。论证比总结更容易检验。

## 先设计，再计划

- 永远不要采用第一个设计。要几个选项的原型，UI 要截图或视频，凭证据来选。
- 让原型回答悬而未决的问题。不要对抽象的计划做对抗性评审，因为评审者会编造永远不会发生的风险。
- 对于共享的包或 API，先要 README 或教程，再倒推回代码。文档成为代理自我校验的靶子。
- 设计定下来之后再要计划。计划的每一步都以一个检查收尾。

## 追问要短

- 一旦聊天里已经有了任务，「做吧」、「继续」、「一直干到完成」就是完整的提示词。
- 换主题时用「新任务」开头。否则这个模式会把这条消息当作下一步。

## 离开之前

- 说一句「我要去睡了」或「我要离开一下」，代理就不会再追问了。
- 把「完成」写成每一轮迭代都能跑的检查，把这个谓词交给 `/loop`。
- 要求从一个指定的基准拉一个全新的 worktree。
- 预先回答代理会停下来问的事，比如「提交前不用问我」。
- 要求记一份决策日志，供事后审计。
- 给一个出口：「如果几小时后真的卡住了，就停下来，写清楚为什么」。

## 一句话纠偏

- 重述目标：「我说的是目标是复现。我还没让你修。」
- 点名原则：「应用 prove it works。给我看真实输出，不是构建日志。」
- 点原则名之所以有效，是因为代理已经读过那条规则。它的回复会说出这条规则改变了哪个决定。
