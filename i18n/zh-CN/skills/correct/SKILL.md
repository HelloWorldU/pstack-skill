# Correct

运营者一直在为这个仓库里同样的错误反复纠正代理。改造这个仓库，让下一个代理没法再犯。

假设每位贡献者都是一个只看得到自己打开过的文件、照抄最近示例、走能编译通过的最短路径的代理。把仓库设计成：从单个文件看显得正确的改动，对整个仓库也正确。

## 找出错误类别

首先，读近期的提交、回退、评审意见、代理指令文件，以及解释变通办法的注释。把错误归成类别。一个错误犯过两次，就算一个类别。

## 在能奏效的最高层级修掉每个类别

1. **用架构消灭它。** 让每份状态只有一个属主，让每项任务只有一种受支持的做法。隐藏内部结构，让错误的 import 直接失败。用单一事实来源取代手工同步的清单。删掉旧做法和代理会去照抄的死代码。
2. **用类型强制约束，让坏状态写不出来。** 如果坏代码仍能编译通过，就加一条 lint 或 CI 检查，其报错要点名应该改用的文件、类型或函数。如果这个模式已经很普遍，就只在改动让它变多时才判失败。
3. **测试行为。** 修掉或删掉任何"即使它调用的每个函数都什么都不返回也仍会通过"的测试。
4. **最后才写文档或代理规则，只写给需要判断力的场合。** 代理跳过它们时不会有任何东西失败。

## 修复并证明

然后现在就修最高频的几个类别，每个类别一个提交。证明每个新检查都能在一次真实的历史错误上失败。在本地和 CI 里跑同一条命令。例外要写在出错行上，附原因、到期时间和一个人类的批准。

## 维护规则表

最后，在代理指令文件里维护一张表，把每条规则和强制执行它的机制配对。当运营者纠正你时，修掉这个错误并补上规则。如果规则本来就在却没有任何机制强制执行，那就是一次重犯——在同一次改动里，在能奏效的最高层级修掉它。当某条规则对应的错误不再可能发生，就把这条规则删掉。

**回复：** 每个类别及其证据、你选择的层级，以及更高层级为什么不可行。
