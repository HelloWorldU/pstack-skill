# 造杠杆

当工作不是琐碎小事时，造一个能干这活的工具，而不是手工去做。

codemod、生成器或脚本每次都以同样的方式干活，而且可以免费重跑。工具是一份评审者可以阅读、可以重跑来检查工作的产物。手工做的改动只能通过重做一遍来复核。一个确定性的脚本把「信我」变成「跑这个」。

默认选择造杠杆。只有当任务确实琐碎时才跳过——就是那种一眼就能看全的两三处明显改动。

- 先手工做第一个单元，学会套路，然后造工具。验证方式：在该单元上重跑工具，与手工版本做 diff。让杠杆可以安全地重跑。
- 编辑用 codemod 或脚本，重复性文件用生成器，分析用「导出到 sqlite 再查询」，验证用可重跑的检查。
- 确定性的杠杆胜过扇出。如果工具能一遍处理完所有单元，就你自己跑。不要把脚本能做的事扇出给代理们去手工执行。
- 当你把工作扇出给子代理时，把杠杆写成它们都要读的一个技能：套路、验证契约、不许碰的围栏，全部放在一份产物里。把它放在代理们的写权限范围之外，让它们没法悄悄改动契约。
- 应用这条原则会产出一个文件。如果你引用了它，但 diff 里没有 codemod、脚本、生成器或代理技能，那你并没有应用它。
- 当工作的寿命超过本次会话时，把杠杆一并提交。

门槛是琐碎与否，而不是是否重复。一次性工作同样值得造杠杆——只要杠杆是让这份工作可以被检查的关键。按照[懒汉协议](../principle-laziness-protocol/SKILL.md)的要求，造一个能干活或能证明干对了的最小脚本，永远不要去造框架。

与[把教训编码进结构](../principle-encode-lessons-in-structure/SKILL.md)不同——那条是把反复出现的指令变成持久的护栏；这条是提升眼前工作的吞吐量和可评审性。要把验证本身脚本化，参见[证明它有效](../principle-prove-it-works/SKILL.md)。
