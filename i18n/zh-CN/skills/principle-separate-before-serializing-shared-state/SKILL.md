# 先分离，再串行化共享状态

当并发执行者可能共享可变状态时，先问它们是否需要同一个可变对象。如果不需要，就消除共享。当共享是真实的，就用结构强制串行化：锁文件、顺序阶段、排他所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写会造成竞态条件——时隐时现、难以复现、调试昂贵。

**模式：**
1. **识别共享的可变状态**（双方都读写的文件、双方都推送的分支、一方定义另一方消费的 API）。
2. **默认：消除共享的写入目标。** 问一句：这些执行者需要一个权威对象，还是只是在发布各自独立的事实？给每个执行者自己的文件、键、分支或状态目录，只在读取/汇报边界处合并。两个工人往一个 `state.json` 里写各自的 `lastX` 字段，仍然是共享修改。`indexer-state.json` + `metrics-state.json` 就不是。
3. **只有当单一共享写入目标是真实不变量时，才做结构化串行化**（锁文件、顺序阶段、单写入者角色，或原子比较交换）。把「我们需要一把锁」当作需要检查的设计坏味道，而不是默认答案。
