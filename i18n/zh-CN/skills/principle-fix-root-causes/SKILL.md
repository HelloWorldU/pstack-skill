# 修复根因

调试时不要修症状。把每个问题追溯到根因，在那里修复。

**为什么：** 症状修复会累积。每个绕过方案都让系统更难推理，而真正的 bug 还在。根因修复前期更慢，但能减少总的调试时间。

**模式：**
- 先复现
- 追问「为什么」，直到撞上根因
- 不要加防御性检查（加一个 nil 检查让崩溃闭嘴，就是症状修复）
- 如果一个绕过方案需要一整段注释来辩解，那就是代码错了（修代码，别修注释）
- 检查的是模式，不只是这一个实例（grep 同样的模式，把所有实例都修掉）
- 卡住的时候就上仪器，别猜（加日志，读真正的报错）
- 如果那个决定性的事实费了很大劲才挖出来，就顺手提出一个廉价、常驻的信号——当初第一眼就能看到它的那种

**重启类 bug：先怀疑状态，再怀疑代码**

当某个东西「重启后就挂」，先怀疑陈旧的持久化状态：配置文件、缓存、锁文件、序列化状态。如果清掉某个状态文件后行为恢复，就把状态校验作为优先修复方向。
