# 维护验证技能

应用一变，特性地图就开始腐化。这个技能是 `/create-verification-skill` 生成的技能（或任何带特性地图的项目本地验证技能）的维护回路。严谨的单位是特性，而不是每一句话：从源码覆盖每个特性文件、实机演练每个特性，但不必把每个要点都逐条终验。

## 结果

三选一，并说明是哪一个：

- **clean** —— 每个特性都有源码和实机覆盖；没有值得交付的东西。不开分支，不开 PR。
- **changed** —— 一个 PR，交付经过证实的文档、工装或地图修正。
- **blocked** —— 覆盖无法完成，或一个已证实的修复无法安全交付。说清楚到底是什么挡住了。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的工装脚本）。运行期间绝不编辑产品代码：地图描述了、而应用已不再具备的行为，要么是文档漂移（修地图），要么是产品回归（报告它，别在文档里糊弄过去）。

## 巡检流程

0. **定位目标。** 找到要维护的验证技能：正文里有启动/驱动章节和特性地图的项目本地技能（通常是 `.cursor/skills/verify-*/`）。有多个候选 → 问用户选哪个；一个都没有 → 停下并指向 `/create-verification-skill`，不要自己编造目标。

1. **索引卫生。** 阅读特性地图的 README 并 glob 它的同级文件。修掉缺失、多余、重复或失效的条目。轻量处理；不生成清单。

2. **源码波次。** 每个特性文件派一个只读子代理，并发启动。每个子代理从源码回答「这个面向用户的特性是怎么工作的？」，带着引用标出可能的文档漂移，并返回一条简洁的实机验证配方。子代理绝不驱动应用，也绝不编辑文件。返回格式：特性摘要 / 源码入口点 / 可能的漂移或无 / 一条配方。

3. **对账。** 每个特性文件都应有一份返回的摘要。把重叠的配方合并成尽可能少的应用状态。抽查被引用的漂移；对判定为干净的结论不要重新证明。扫一遍近期的改动，找出地图里缺失的面向用户的界面——宣布某个界面缺失之前，必须给出具体的源码路径。

4. **实机巡检。** 即使源码看起来干净也必须做。协调者掌握全部驱动权；遵循验证技能自己的启动模型——服务器和 UI 用一个长驻实例串行驱动，短生命周期的 CLI 则每次驱动都开一个全新的隔离会话（由该技能的「启动」一节决定，不是这里）。每个特性至少演练一次，并且无论发生什么失败，整个巡检都守住三条不变量：（1）绝不驱动一个自它上次做出意外行为以来你还没做过健康检查的实例——首次驱动前先 doctor，以会话为单位的每次新会话都 doctor，任何一次驱动失败后再 doctor 一次；如果 doctor 看不到那个失败（进程健康但 UI 状态卡死），就重置到已知状态或重启，而不是心存侥幸；（2）至今已采集的证据在每次清理后都还在，到它指定的位置核实，而不是想当然；（3）一次驱动所启动的东西，不得活过这次驱动的用途——无论会话是卡住了、已退出还是共享的，失败迭代留下的残渣都要清理（共享实例则清残渣，而不是清实例）。由技能漂移导致的 doctor 失败本身就是漂移：在编辑范围内修掉并重试一次——被这次修复弄失效的东西才重启，别的不动——然后才能把本次巡检判为 `blocked`。一个到不了的特性，只有给出具体的前置条件（认证、授权、操作系统、外部状态）和已尝试的路径，才能记为 `verified-unreachable`；如果地图漏写了这个前置条件，那也是漂移。分诊中产生的任何工装修复，都要实机重新驱动过之后才能交付。最终拆除在整轮最后一次驱动之后进行——包括那些复验——这样没有任何东西活过这一整轮（证据按技能要求保留）。

5. **分诊。** 用户视角的描述错了或缺失 → 文档漂移，修掉。行为正常但工装卸不动 → 工装缺口，修掉；工装修复遵循与生成时相同的辅助脚本规则（脚本可执行、调用方式写进技能正文）。应用行为确实坏了 → 产品缺口；记录下来交给用户，别放进这个 PR。

6. **交付或收工。** changed：一个只装经过证实的修正的 PR，先重读每个被改的文件。clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

把简要的运行笔记（覆盖的特性、到不了的前置条件、确认的漂移、结果）记在一个临时位置；不要提交它们。
