# 不留注释

派生 Comment Sicko。处理被接受的发现。

尊重 Comment Sicko 的新鲜视角。

## 范围

使用调用方给的文件或 diff。否则用当前相对基准分支（默认 `main`）的 diff，包括工作区。

## 步骤

1. 用 `subagent_type: "comment-sicko"` 派生 `Task`。把范围传过去。按照 **poteto-mode** 技能的「子代理」一节，为每个子代理挑选适合这项任务的推理级别和快速/标准速度。不要复述它的规则。
2. 检查它的报告和 diff。驳回以下情况：改动应用代码、越出范围、删除受例外保护的注释、`MUST KILL` 理由说错，以及把刻意保留的代码当成有罪的标记。针对「我们的代码出人意料」的 reshape 类标记仍然可行动。不要恢复那些注释。一个「保留」结论只有在证明了它关乎我们无法改变的东西时才成立。审计漏掉的、在范围内的 lint 和 TypeScript 抑制注释。正确性或安全性的抑制注释仍然是可行动的 `MUST KILL`。只有带着确切例外和范围内证据时，才恢复已删除的注释。在接受单薄的 `IMPORTANT` 或 `do not remove` 类的「杀」或「留」之前，先在相关符号上跑 `/how` 或 `/why`。如果一个「杀」有歧义，就不要恢复。如果一个「留」被驳倒或仍有歧义，就删掉它。对于第一份被驳回的报告：回滚其改动、指名失败原因后重跑一次。第二份再被驳回，就把它记为未决上报，并让 `/no-comments` 失败。
3. 对已接受的琐碎标记直接修复：删掉死路径、去掉一个参数、或改用真正的 API。如果任何修复需要先定形态，就为已接受的集合及其周边代码跑一次 `/architect`。停在草图阶段。Architect 出形态，第 4 步负责实现。
4. 在范围内实现最小的根因修复。移除每一个被点名的 workaround。如果根因在范围之外，落地最小的范围内修复，把其余的记为未决上报。**principle-fix-root-causes** 和 **principle-redesign-from-first-principles** 技能只用于指导意图。它们都不授权扩大围栏，也不授权修复围栏之外的实例。永远不要外挂症状守卫。
5. 约束类注释写着 `do not remove`、`do not change wording` 或 `talk to X before changing` 这类话。关乎我们无法改变之物的「保留」结论就保留。提供范围内最便宜的类型、运行时、测试或 CI lint 编码化方案。等待交互式批准。无人值守和评测场景需要调用方预先批准。批准后，先编码化再删除。否则删除注释、把该约束记为未决上报，并草拟范围外的工作。
6. 汇报删除数量、恢复的注释、重跑次数、architect 草图、修复、编码化提议、已完成的编码化、未编码化的约束，以及其他未决工作。
