# 创建验证技能

每个认真的项目都需要一种脚本化的方式来驱动真实应用并证明行为：启动它，像用户那样操作一个功能，并捕获证据。本技能把它生成为一个为仓库量身定制的项目本地技能（`.cursor/skills/verify-<app>/`）。生成器的输出是写给下一个代理的，不是写给人的：它会被一个从未见过这个应用的代理在任务中途、毫无预热地阅读。

## 1. 采访仓库，而不是用户

从代码库中回答下面这些问题，只把观察不到的留给用户：

- **界面（Surface）：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个仓库可以有多个；挑主要的那个，记下其余的。
- **运行（Run）：** 应用如何在本地启动？优先用仓库自己文档里的开发命令（package scripts、Makefile、README 快速上手）。记下端口、环境变量、种子数据、鉴权。
- **驱动（Drive）：** 代理如何以编程方式与它交互？先看现成的装置——Playwright/Cypress 规格、expect 脚本、PTY 辅助工具、可 curl 的端点、调试端口。然后才选通用配方：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 装置，服务用纯 HTTP。
- **观察（Observe）：** 能捕获什么证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离（Isolate）：** 两个实例能否并排运行（端口、数据目录、配置档案）？如果不能，在生成的技能里明说：拒绝双重驱动共享实例，胜过搞坏用户的会话。

如果检出的代码原样构建不了或启动不了，在生成之前先修好（或者精确地报告问题）；对着坏掉的基底写出的技能会教出错误的步骤。当某个无关的缺失资源挡住启动时（API 从不提供服务的静态目录、示例配置），生成的技能可以创建它——明确标记为验证脚手架——并在清理时移除。

## 2. 生成技能

编写 `.cursor/skills/verify-<app>/SKILL.md`，带 YAML frontmatter（`name: verify-<app>`，以及一个点明应用、界面和何时使用它的 `description`——没有 frontmatter，技能永远不会注册），并包含以下各节，每节都扎根于采访的实际发现（不留占位符）：

- **启动（Launch）：** 为验证启动应用的确切命令，以及如何判定它就绪（一行日志、一个提示符）。启动必须能从空数据目录达到可用状态，包括所有迁移和种子数据。就绪意味着可用，而不只是有个进程在应答。数据库健康检查可能通过，而它的初始化脚本还在运行。包含拆除步骤。对短命的 CLI 或 TUI，没有需要保活的服务器：启动意味着构建一次二进制（或安装依赖），然后让每次驱动在各自隔离的 PTY 或 tmux 会话中进行。
- **体检（Doctor）：** 一个只读检查，回答「这个实例值得驱动吗？」——进程在跑、版本/构建正确、端口归我们、鉴权有效。每当有任何地方看起来不对，代理就先跑这个检查。
- **驱动（Drive）：** 装置配方，用来自这个仓库的真实选择器/命令，而不是示例。优先稳定的句柄（ARIA 标签、data 属性、提示字符串、路由路径），而不是坐标和 Tab 顺序。
- **证据（Evidence）：** 一次证明要捕获什么、放在哪里。写明证明标准：走真实用户路径，而不是内部 setter 或测试专用端点；捕获动作及其产生的状态，而不只是最终画面；连同可见结果一起验证副作用（写入的文件、插入的行、发出的消息）；只在生产边界本就隔离了外部系统的地方使用 mock。当安全路径是 dry-run 或测试模式时，要通过观察（文件、网络、git 引用）验证它实际跳过了什么，而不是相信它的名字：有些 dry-run 仍然会碰网络或打开浏览器。
- **清理（Cleanup）：** 如何拆除本次运行创建的实例。永远不要按进程名杀进程；杀你启动的那些。清理移除实例和临时状态，绝不动证据：证明产物要在拆除后存活，存放在技能点名的位置。
- **辅助工具（Helpers）：** 技能附带的任何脚本都是可执行的，且其调用方式展示在技能正文里。需要读者逆向工程的辅助工具不是辅助工具。

## 3. 播下功能地图的种子

创建 `.cursor/skills/verify-<app>/features/README.md`，并为你能识别出的每个面向用户的功能各建一个文件（先从最前面的 3-5 个开始，从路由、命令、菜单或文档里找）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 的结构：一个 README 索引，加每个功能一个文件。每个文件从用户视角回答：这个功能是什么、如何到达、如何用装置驱动它、什么可观察的最终状态证明它工作。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某段旅程需要的前置条件，这段旅程就报告失败，原因写进该功能的 `Gotchas`。永远不要为了让旅程通过而削弱它。功能地图是仓库持续维护的验证来源；当地图列出了其他入口时，只驱动一个顺手入口的证明是不完整的。

## 4. 交付之前先证明生成的技能

把它自己的说明端到端跑一遍：启动、体检、驱动**一个**已映射的功能（一个就够；地图的存在就是为了让以后的运行覆盖其余部分）、捕获证据、清理。清理之后，确认证据仍在点名的位置——把证据一起吃掉的清理算这一步失败。修掉失败之处，并且每次迭代失败后也要运行生成的清理，让坏掉的尝试不会留下孤儿进程和端口。从未执行过的生成技能是草稿，不是交付物。如果你是在真实目标的替身里证明的（用容器代替全新虚拟机、用本地栈代替远程栈），列出替身做过而目标不会做的每一个设置步骤。这些步骤保持未验证状态，直到真实目标上的一次运行覆盖它们。

## 5. 提供维护闭环

把 `/maintain-verification-skill` 指给用户，用来在应用变化时保持功能地图的诚实。只在用户问起时才建议节奏。
