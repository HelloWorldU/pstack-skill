# Notes 验证地图

本目录是验证 Notes 面向用户行为的维护中的事实来源。驱动应用之前先读本索引，然后把对应的功能文件当作操作配方使用。

## 基线前置条件

- 用一次性数据目录在 `http://127.0.0.1:4173` 启动 Notes。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，使并发运行之间不共享状态。
- 预置标题为 `Quarterly plan` 和 `Grocery list` 的便签。
- 把 `control-notes` 和 `notes` CLI 放到 `PATH` 上。
- 运行 `control-notes doctor`，要求它报告预期的 URL、数据目录和构建版本。
- 永远不要驱动不是由本次验证运行启动的实例。

## 驱动约定

- 除非配方自身的前置条件另有说明，否则每个配方都从基线状态开始。
- 优先使用 ARIA 角色和可访问名称，而不是 CSS 选择器或 DOM 位置。
- 把每条命令当作字面内容。带引号的名称和 flag 保持原样。
- 浏览器操作通过 `control-notes browser` 执行。
- 终端操作通过 `control-notes cli -- <command>` 执行。
- 发生变更后恢复预置数据。清理时不要删除证据产物。

## 取证与跳过报告

- 捕获用户动作及其产生的状态，而不只是最终画面。
- UI 证据包括一份 ARIA 快照和一张能看到应用标识的截图。
- CLI 证据包括命令、stdout、stderr 和退出码。
- 变更类证据包括对存储值的只读第二视图。
- 每份产物都要记录功能 ID 和使用的入口。
- 报告走不通的路径时，附上尝试过的命令和未满足的前置条件。
- 不要把跳过未走的入口报告为已通过其他路径验证。

## 功能条目契约

每个功能文件以一个 H1 标题和一段描述用户可见行为的文字开头。然后严格按以下顺序使用四个 H2 小节。

1. `Sub-features` 列出简短 ID，每个行为一行。
2. `How to get to it (user POV)` 列出每一个用户入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用带标签的列表项把每个用户动作与确切的命令和可观察结果配对。
4. `Gotchas` 列出可能浪费一次验证运行或使其失效的陷阱。

不要把实现细节写进地图。只点名用户路径、稳定的句柄、所需状态、命令和可观察的证据。

## 功能

- [创建便签](./create-note.md) 覆盖浏览器和 CLI 创建、取消、持久化和清理。
- [搜索便签](./search.md) 覆盖工具栏、键盘和 CLI 搜索，以及匹配、空结果和清除状态。
