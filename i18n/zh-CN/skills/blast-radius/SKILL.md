# Blast radius

在改动发布之前，找出它会在别处弄坏什么。适用于"X 的爆炸半径"、"这会弄坏什么"，或评审一个你还信不过的小 diff。

与 `how` 和 `why` 互为补充。`how` 告诉你代码做了什么。`why` 告诉你它为什么长成那样。Blast radius 告诉你它会在别处弄坏什么。

列出调用方不是这份工作的内容。代理一秒钟就能 grep 出来。这份工作是 grep 不会告诉你的那些破坏。

## 别信自己写的说明

一份听起来有道理的爆炸半径说明一文不值。不管它是真是假，读起来都同样有说服力。所以不要把说明交回去就完事。找到整件事所依赖的那一两条事实，通过运行代码来证明它们。

### 你有多确定

对于改动安全性所依赖的每条事实，在成本允许的前提下尽可能把它推进到下面这个清单的更深处，并说明它停在了哪里。

1. 你说的。单独看一文不值。
2. 你指出了那行代码。一个真实的 `file:line`，或者库自身的源码。
3. 你论证了坏情况不可能发生。你一步步走完了失败路径，它到不了那一步。
4. 你跑了它。一个脚本或测试，调用真实代码，如果你错了就会大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常就是一个小脚本：导入应用发布的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读改动。读 diff、它新增/修改/删除了哪些符号、它现在的行为有什么不同——包括 diff 没有明说的部分。用 `why` 的第 2 步拉取 PR 和提交。
2. 找到那条"因为有它所以安全"的事实。大多数看起来有风险的改动，安全是因为某一条事实，比如"这个调用只丢弃已经失效的缓存条目，别的什么都不做"。找到那条事实。只要它成立，大多数风险场景就一次性排除了。把时间花在这里，而不是花在一张长长的"也许"清单上。
3. 看 grep 止步的地方。读你调用的库的源码，检查它的锁定版本和任何本地补丁。弄清楚事情何时运行：微任务、卸载与清理、Solid 与 React 的差异。追踪符号搜索漏掉的东西：API 返回的 JSON、数据库列、线上协议格式、读取同样字节的另一种语言、功能开关、下游三跳之外的代码。
4. 诚实地对待每个风险。给它一个真实的发生概率和真实的代价。保留你确认过的风险。把你检查过并排除的那些单独列出。规则与 `why` 相同：引用真实的 `file:line`，一次什么都没搜到的搜索仍然是一个答案，永远不要编造调用方或 API。
5. 证明那条事实。写一个调用真实代码的脚本或测试，运行它，并把结果贴出来。
6. 对于大改动或影响面宽的改动，用 `arena` 的方式来做：向多个模型问同一个问题，合并答案。不同的模型能抓到不同的真实 bug。

## 交付什么

- **它做了什么。** 改动内容，包括不明显的部分。
- **那条"因为有它所以安全"的事实。** 陈述它，说明你把它推进到了哪一步，并展示证明。如果证明不了，就写明"未证明"。
- **风险。** 每条说明它会怎么坏、`file:line`、发生概率和严重程度，以及如何检查。重要的那些要贴上证明。
- **已排除。** 你检查了什么、为什么没问题。
- **合并之前。** 能抓住真实 bug 的最便宜的测试或复现，包括你写的脚本。

用 `unslop` 过一遍成稿，引用真实代码，在发往任何公开场合之前删掉所有私密内容。

**回复：** 上述说明，其中那条安全事实要么已证明，要么标记为未证明。
