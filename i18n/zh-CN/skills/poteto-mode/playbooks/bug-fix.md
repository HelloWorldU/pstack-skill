### Bug 修复

**你拥有这个任务。规划、评审、验证。** 把调查和修复委托给子代理，你自己保持主导。按 Subagents 一节为每个子代理挑选适合该任务的推理级别和快速或标准速度。

讲科学。每一行交付的代码都能追溯到运行时证据。"也许有用"的双保险是假设，不是修复，不交付。当证据推翻一个假设时，回滚它促成的改动。只交付证据支持的最小改动，一行都不多。

1. 通过控制技能（见"不可妥协项"）在匹配的界面上亲自复现，即使某个调试或插桩协议说让用户去复现也一样。只有当你能陈述控制界面为何够不到目标的具体理由、并且已经把它驱动到极限之后，才去问用户。如果无法直接复现，就合成触发条件、收紧前提、或插桩，直到它发作。
2. 对原因做二分查找。列出候选假设，逐一排除直到只剩一个。用 `how` 扫一遍受影响的子系统、用 **why** 技能查回归历史，为假设提供种子。每一轮，选能切掉最多剩余问题空间的那一刀，取运行时证据，排除。程序状态不清楚时，加插桩或日志，在代码运行时读它。不要猜。漫长或顽固的追查用 Cursor 的 `/loop` 命令驱动。在第 3 步的 architect/interrogate 扇出之前，用运行时证据确认幸存的*机制*。
3. 规划修复。跨越函数边界就先走 `architect`。用你配置的修 bug 模型（默认 `grok-4.7-xhigh-fast`）把实现委托给一个子代理，并给出明确的范围。
4. 在同一个界面上验证。最初的复现路径现在通过。"不确定"或界面不对都不算通过——标记出来。单元测试展示的是分支行为，不是 bug 不存在。
5. 组织提交，让失败的复现先于修复进入 git 历史。当 bug 有廉价的本地测试路径时，见 **tdd** 技能的"先失败测试"节奏；测试昂贵、重度依赖集成或说不清时跳过。
   这正是 **sequence-verifiable-units** 原则技能的标准用法——失败的测试在前，修复叠在其上。
6. 运行 **Opening a PR**（开启 PR）手册。

**回复：** 坏在哪里、根因、修复、你如何验证。逐字粘贴先失败后通过的复现输出。
