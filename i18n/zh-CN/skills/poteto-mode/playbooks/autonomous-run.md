### 自主运行（Autonomous run）

**你拥有退出条件。先定义"完成"，然后不停顿地推进到它。**

1. 在第一次迭代之前，把退出条件陈述为一个可检查的谓词（测试全绿、复现路径已修复、全部 N 个 PR 已合并、像素差异为零）。
2. 用 Cursor 的 `/loop` 命令（内置功能，不是 pstack 技能）选择唤醒机制。如果有要观察的事件（CI、一次合并、某个 ref 前进），就派一个守望者子代理在事件发生时唤醒你，并配一个较长的定时心跳作为兜底。没有事件就配一个固定间隔的心跳，间隔大小按"结果什么时候值得重新检查"来定。按 Subagents 一节为每个子代理挑选适合该任务的推理级别和快速或标准速度。
3. 每次迭代只做证据支持的最小改动，对照谓词验证它，有推进就提交，没帮助就丢弃改动。"也许有用"的双保险式改动要回滚掉，而不是留着搭车。
   通过 **sequence-verifiable-units** 原则技能为工作排序：先验证当前单元再做下一个，而不是把检查堆到最后批量进行。
4. 运行途中的发现归你处理。损坏的技能、相关的 bug、不稳定的验证器、评审噪音、工具故障、没人管的后续事项、以及可修复的漂移，都由你通过 poteto-mode 自行处理。带外的修复放进它们自己的 PR。不要把可逆的工作甩给人类，也不要使用 `AskQuestion`。只有这些情况才上报：不可逆的操作、实验无法裁决的真正产品或偏好取舍、或者真正的死胡同。始终以谓词为主驱动，每次旁路修复之后回到它上面。
5. 通过 **show-me-your-work** 技能为每次迭代留下检查点：一行记录改动了什么、谓词是否前进。
6. 谓词满足时才停止。平台期不是停止的理由——继续推进，并调整方法冲过它。遇到真正的死胡同就上报，而不是空转；永远不要靠放宽谓词来宣布胜利。

**回复：** 退出条件、运行的迭代次数、落地的内容、丢弃的内容、谓词的最终状态。
