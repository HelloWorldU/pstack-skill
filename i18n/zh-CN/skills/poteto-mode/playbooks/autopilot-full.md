### 全自动驾驶（Autopilot-full）

**你拥有判定权，但永远不拥有 PR。每个 PR 由一名负责人从构建一路护送到合并，而在你的蜂群——一个从未写过这些代码的蜂群——证明即将落地的代码之前，任何东西都不许合并。**

一次判定覆盖一个补丁，一次绿色 CI 覆盖一个头部（head）。第 4 步的完整蜂群只运行一次，只有重大变更才会再跑一次。`playbooks/shipping.md` 中的 patch-id 规则可以沿用某条泳道的结果，而每个新头部都需要自己的绿色 CI。

1. **操作员的闸门优先。** 授权只覆盖队列内的条目，所以操作员指明归自己的条目和队列之外的 PR 到可合并（merge-ready）就必须停下。要求陈述计划不等于放行。
2. **每个 PR 派一名负责人，并把它的工作放在接替者能找到的地方。** 整个项目只解析一次代码托管平台（forge）。默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功且 Origin 能解析该仓库，所有 PR 操作都用 `origin pr`。否则留在 `gh` 上并记录这次回退。永远不要要求 Graphite（`gt`）。每名负责人是一个 Cursor 云端代理：负责构建，按 `playbooks/opening-a-pr.md` 开启自己的 PR，在真实产物上证明改动，按 `playbooks/babysit.md` 看护到全绿，并在第 4、5 步放行后合并。

   尽早开启 PR，让 CI 和机器人与工作并行运行。代码只有在完成去泔水（`cursor-team-kit` 插件的 `deslop` 技能（`/deslop`））和 `/no-comments` 这两道之后才算就绪，这样完整蜂群运行在成品代码上。然后变基到当前主干，并在自我验证之前报告"代码就绪"的头部，让验证运行在补丁将要落地的基座上。之后的每个头部都要报告；自我验证、CI、看护都完成后即为可合并。修复轮次停留在那个基座上，除非主干出现冲突或弄坏 CI——因为每次变基都会重启 CI。在"代码就绪"推送之前，以及之后任何需要验证器的推送之前，先在已提交的头部上运行仓库针对受影响路径的检查。

   假设虚拟机随时会死。启动后尽快推送，并按 **show-me-your-work** 技能在根代理的存储中（路径在系统提示词里）开启一条决策轨迹；之后每完成一个值得保留的单元就推送一次。谁派生子代理，谁就在该存储中记录它的 id、状态，以及根据同类历史运行得出的"超过此时长视为卡死"的运行时间，这样父代理死掉后根代理能探测它。只强推自己的分支，`--force-with-lease` 钉在你上次推送或接手时的 SHA 上；发现任何不是你发起的推送，停下来报告根代理。
3. **让负责人从主干并行出发，永远不堆叠，** 这样每个 PR 各自独立落地。
4. **蜂群验证一次。** 完整蜂群只跑一次，在"代码就绪"的头部上。只有出现新行为、重新设计或大篇幅新 diff 时才再跑一次完整蜂群。一次变基、一次合并冲突解决或一个小修复，只在新头部上派一个验证器。按 **swarm** 技能在代码就绪的 SHA 上扇出多个相互独立的验证器。它们重跑各道闸门，通过真实界面的控制技能（如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或指定的驱动器，在现场证明承重行为，并审计 diff。没有现场泳道，判定就不算干净；在你审计"可合并"报告的回执之前也不算——因为没有任何泳道会相信一个自己没有检查过的说法。

   把每一条已证实的发现——不管泳道给它贴了什么标签——合并成一次前推修复（fix-forward）发给负责人，并附上一个覆盖所有存在同一缺陷位置的红色测试。主干在没有该 PR 时就表现出的缺陷记在主干的账上，不阻挡该 PR；但该 PR 复制过来或新触及的缺陷归该 PR 自己。永远不要亲自推送修复——每个分支只有一个写入者——负责人卡死就换掉它。
5. **负责人只合并你验证过、且在将要落地的主干上测试过的内容。** 光有绿色 CI 永远不能授权合并。蜂群各泳道一旦启动，合并准备就变基到当前主干、报告新头部、等待 CI 变绿。

   合并前一刻，拉取主干并问一句：主干的改动是否会影响这个补丁——因为主干每动一下都变基是没完没了的。当将要落地的代码从未被测试过时，变基并等待 CI：比如存在冲突、双方都改过的文件、或该 PR 运行哪些检查发生了变化。双方都改过锁文件时，如果冻结安装（frozen install）能在合并结果上通过、且该 PR 改动的包在合并结果上解析出的版本与头部一致，就无需变基——因为那次安装测试的正是将要落地的锁文件；安装失败则说明必须靠变基来修复它。当主干改动了补丁的调用方或补丁依赖的东西（如它调用的代码或某个依赖版本），在合并结果上运行该补丁的检查，通过就合并。其余情况直接合并。如果主干的变化将迫使合并准备之后再做第三次变基，暂停并向根代理报告，由根代理为这些相撞的工作排序。
6. **运行根层级。** 任何放松闸门的动作——比如提高预算或增加白名单条目——都需要一名验证器的证明，再加上你当场新签的会签，因为想要全绿的正是负责人自己。在覆盖审批权的授权下，那次会签就是审批，负责人对它的记录要指向你的会签，供泳道查验。被禁用或软性失败的检查一律上报，因为它已经不再守护每一种情况。永远不要给出或绕过由托管平台强制执行的审批——没有任何会签能覆盖它。

   操作员放行后，装上 `/loop 1h` 持续审计，直到没有已委派的工作剩下——因为长跑会漂移，代理会悄无声息地停摆。每个 tick 从主干重读这本行动手册，并修复漂移——比如未报告的头部或未登记的代理——让对应负责人补记，因为漂移是记录上的缺口，不是停摆。它探测每一个代理，一直下探到叶子泳道，并且按副作用评判每个代理，因为状态文字和摘要可能掩盖一个卡死的子代理。代理报错、无法开启新一轮、或超过"卡死时长"仍无新产出，就算卡死；负责人到第一个 tick 既没推送也没写轨迹行，同样算卡死。在等你或操作员答复的不算卡死——去答复它。立刻替换卡死的代理，不等它的停止落地。某个 tick 给操作员带来了变化，结束时按 **ketchup** 技能让他跟上进度；什么都没改变的 tick 保持安静。
7. **操作员叫停就立刻停手。** 暂停令以"零写入"命令的形式传达到每一名负责人。各自报告自己所处的位置，并保留自己的任务简报，直到操作员解除。

**回复：** 按 **ketchup** 技能让操作员跟上进度，覆盖每个 PR 的状态和判定、合并了什么、会签了哪些以及为什么、以及仍敞开的操作员闸门，并附上各 PR 和决策轨迹的链接。
