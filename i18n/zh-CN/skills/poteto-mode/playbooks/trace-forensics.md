### Trace 取证

**你拥有来自工件的诊断。**

区别于给活进程插桩的**运行时取证**。这里捕获已经存在。工件是固定数据集，读它，不要重跑它。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或 trace 解析器，spindump 用文本编辑器，heapsnapshot 用你的堆工具。

1. 识别格式并用正确的工具加载。在子代理中解析大工件（**principle-guard-the-context-window** 技能），把归约后的发现留在主线程。按 Subagents 一节为每个子代理选择适合任务的推理等级和 fast 或 standard 速度。
2. 把原始工件变换成可查询的形态。把 trace 或堆快照灌进 sqlite，每个样本、帧或节点一行。先到达可查询形态再开始读。
3. 收窄到原因。查询占用时间最多的帧，沿调用树走到热路径。对泄漏，沿着从泄漏对象到 GC root 的 retainer 链走。对 spindump，找到卡在 CPU 上或被阻塞的线程及其等待原因。
4. 归因到源码。通过工件自带的符号把热帧映射到文件、符号和行。没有源码映射的帧还不算诊断。解析符号，或者明说工件不携带它们。
5. 如果有成对捕获，diff 前后工件以确认。否则，把发现标记为该工件支持的最强假设，而不是已确认的原因。
6. 交回带引用的诊断，除非被要求不给修复。原因已知后路由到 Bug fix 或 Perf issue。吞吐量检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 工件与格式、归约后的发现、源码位置、工件路径、是否有成对捕获确认了它。
