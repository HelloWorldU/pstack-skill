### 重构

**你拥有契约。结构会变。行为不会。** 区别于添加行为的 Feature 和纠正行为的 Bug fix。

如果清理暴露出缺失的功能或真正的 bug，拆出去，先对照钉住的契约交付结构性改动。允许重新设计，但要点名并路由到 Feature。大型或横切的结构性工作属于 **figure-it-out** 技能。本行动手册处理聚焦到中等规模的改动。

1. 先钉住行为契约。在受影响子系统上运行 **how** 技能以了解契约，然后写一个刻画测试、快照或等价性支架，在任何结构移动之前捕获当前行为。如果该区域没有覆盖，先写钉子再碰结构。类型检查和 lint 不是钉子。
2. 按 **principle-model-the-domain** 说出代码缺失的结构名字。形状已经清晰且局部时，无聊的代码就留着。重塑必须删掉分支或非法状态，而不是增加间接层。
3. 说出目标形状。陈述如果今天构建，模块布局、类型和调用图应该是什么样（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。如果目标跨越函数边界，在移动之前运行 **architect** 技能对形状做并行设计探索。
4. 先减后加。在引入新形状之前，删除死代码、折叠单调用者包装、去掉冗余校验器、移除孤儿引用（**principle-subtract-before-you-add**）。能到达目标形状的最小改动才交付（**principle-laziness-protocol**）。"可能有帮助"的投机清理会被回退。
5. 以保持行为的小步移动，每步保持钉子常绿。对 API 重塑，迁移每个调用者并在同一波删除旧 API（**principle-migrate-callers-then-delete-legacy-apis**）。不要兼容垫片，不要新旧并行路径。对照实际文件抽查每个重命名。重命名会悄无声息地漏掉字符串、散文和反向引用里的用法。把机械编辑委托给子代理，使用你配置的 refactoring 模型（默认 `grok-4.7-xhigh-fast`），并给出具体范围（文件路径、被移动的名字、要保持的行为）。按 Subagents 一节为每个子代理选择适合任务的推理等级和 fast 或 standard 速度。
6. 在真实工件上证明行为未变，而不是"能编译"（**principle-prove-it-works**）。对更大的重塑，运行等价性检查：一个 diff 新旧输出的脚本、一段录制基线对新代码重放、或通过相关控制技能在匹配表面上的冒烟运行。
7. 确认改动值得保留。成功度量是读者负担降低（**principle-minimize-reader-load**）。如果 diff 没有在任何地方降低读者负担，回退它。
8. Rebase 成小的有序提交。一个减法提交，然后是重塑，然后是后续清理。用 **sequence-verifiable-units** 原则技能塑造它们，让每一段保持行为的切片在下一段之前保持常绿。运行 **Opening a PR**。

**回复：** 改变了的结构、你对照它持有的钉子、等价性证明、读者负担差值、交付了什么、回退了什么。没有新行为。
