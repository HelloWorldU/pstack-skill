# Automate me

一个引导式流程，把用户的工作惯例变成代理会遵循的技能。产出是一个为他们量身定制的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

本技能编排另外三个技能：一次内联的挖掘（见第 1 步）、Cursor 内置的 `create-skill`（负责撰写），以及 **unslop** 技能（负责文风纪律）。它负责把它们串起来，而不是替代它们。

## 流程

### 0. 检查是否已有技能

递归查找 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md` 中与用户名号匹配的条目。mode 技能可以放在个人分类目录里（`.cursor/skills/<handle>/`），不一定在顶层。如果已存在，用 `AskQuestion` 确认意图（除非他们已经说了"更新我的技能"之类的话）：

- 更新现有技能（重复运行时的默认选项）
- 从头开始（很少见，动手前先问为什么）

更新模式会改变后续流程：
- 第 1 步只挖掘技能上次编辑之后的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是有什么变化或遗漏，而不是从零开始要捕捉什么。
- 第 4 步就地编辑现有文件。保留用户没有推翻的小节。修订有新证据的小节。只为真正的新规则新增小节。

### 1. 挖掘历史

扇出之前，先定位当前工作区的对话记录。系统提示词里写着该工作区的 `agent-transcripts/` 目录。只用那个路径。不要跨 `~/.cursor/projects/*/` 去 glob。那会跨越工作区边界，读到无关项目的私密对话。

在这个范围内调查近期的代理对话，寻找反复出现的模式。派多个并行子代理分别挖掘历史切片（例如最近 2-4 周，切成 3 片，让每片都有足够材料）。按 **poteto-mode** 技能的 Subagents 一节，为每个子代理选择合适的推理等级和快速或标准速度。每个切片挖掘子代理阅读父代理提供的工作区级路径下的对话记录，寻找下列信号，并返回一份简短的结构化模式清单，附证据指针。默认值得搜寻的信号：

- 回复偏好（长度、语气、格式、"说人话"式的纠正）
- 委派习惯（子代理、模型、专门的工作流、并行度）
- 验证姿态（什么算"完成"、单元测试还是实际复现、评审者）
- 代码与文风纪律（风格、引用的原则、lint/格式化工具）
- 流程惯例（worktree、提交、PR、评审/合并工具）
- 元偏好（在任务途中修技能、提议新技能）

把一个信号升格之前，先跨切片交叉核对。在 2 个以上切片中出现的模式是高置信度的。孤立信号很弱，通常会被丢弃。

### 2. 直接问用户

挖掘抓不到尚未暴露出来的意图。用 `AskQuestion` 工具（结构化多选），而不是让用户从零开始打字。

形式：一到两个问题，每个 4-6 个选项，分类问题用 `allow_multiple: true`。先问宽泛的（"哪些方面最重要？"），再针对选中的领域用具体选项追问。结构化轮次之后，用一个自由聊天问题接住选项漏掉的东西。

不要一口气抛 20 个问题。

### 3. 归类发现

把合并后的信号归成若干小节。常见的有（只用适用的）：

- **回复风格**：长度、语气、格式。
- **自主权**：不问就做多少、MCP 工具的使用。
- **先理解**：在界定或调查一个改动时该用哪些技能。
- **子代理**：默认策略、并行度、模型与任务的匹配、专门工作流。
- **文风/代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证技能、实际测试工具。
- **流程**：git worktree、提交、PR、评审/合并工具。
- **技能**：写技能的习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了这种形态。读它来把握颗粒度。不要照抄它的内容。用户的规则和 poteto-mode 的规则不一样。

### 4. 起草技能

用 Cursor 内置的 `create-skill` 技能来撰写。放置位置：

- 路径：保留已有 mode 技能的分类目录。新建 mode 时，如果仓库已为该名号建立了个人分类目录，用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认放在项目里的 `.cursor/skills/<handle>-mode/SKILL.md`（若用户想要个人技能，则放 `~/.cursor/skills/<handle>-mode/`）。
- 名号：用户的名字或自选标识。
- frontmatter 的 `description`：以他们的名字 + `/<handle>-mode` + "按他们的风格工作"作为触发条件，而不是"写代码"或"评审 PR"这类通用关键词。
- frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为单个 YAML 标量。当标点或换行需要时，加引号或用 `description: >-` 加缩进续行。
- frontmatter 默认 `disable-model-invocation: true`。只有当用户明确希望自己的 mode 每一轮都生效时才去掉。

### 5. 打磨文风

对每一行应用 **unslop** 技能和 `create-skill` 的写作准则。

把草稿给用户看并收集反馈。预期会迭代多轮。毫不留情地删。mode 技能不是说明书。

### 6. 落地

在从 main 切出的 worktree 里工作。提交并开 PR。不要直接推到 main。

## 护栏

- **不要对单次对话过拟合。** 说过一次、另一次又被推翻的偏好是噪声。写入规则之前要求出现多个实例。
- **不要耍小聪明。** 复述其他技能的内容、发明比喻、给代理读者写"诗意"散文，都是有成本无收益。保持可操作性。
- **引用，不要内联。** 用户依赖的其他技能应以路径引用的形式出现，而不是粘贴摘录。他们在别处维护的原则文档同理。
- **小节保持最小化。** 只有当用户在某个方向有具体的、非默认的规则时才加小节。"清晰沟通"不算一个小节。"短段落。比较选项时用表格。只在各项真正并列时才用列表。"才算。
- **命名惯例保持通用。** 祈使句里用"用户"或"人类"，不要写作者的名字。
- **不要强行对称。** 如果用户没有值得写下来的流程规则，就整个跳过 Process 小节。

## 评估

`-mode` 技能是主观产出。`create-skill` 式的测试/迭代 benchmark 循环在这里没用。和用户一起做感觉检查：读起来像他吗？漏了什么吗？然后交付。

只有当技能的触发准确率在实践中真成了问题，才跑一轮 description 优化循环。

## 何时不要用

- 用户想要的是针对具体任务的技能（而不是工作惯例）：只用 `create-skill`，不需要挖掘。
- 用户想捕捉一个狭窄的工作流（例如"我怎么写提交信息"）。那是普通技能，不是 mode 技能。
