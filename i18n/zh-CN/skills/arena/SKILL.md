# Arena

在启动任何东西之前，先建一个待办清单，每个阶段一条（出题、扇出、交叉评审、选定、嫁接、验证）。

## 阶段 A：出题

每个候选者拿到同样的提示词，所以提示词就是契约。

1. 说明每个候选者要产出的产物是什么。
2. 推导评分量规：针对*这个*任务，3-6 条具体的、可打分的成功标准。它是阶段 D 里挑选者的工具。候选者只看得到任务本身。
3. 挑选 runner。使用 `~/.cursor/rules/pstack-models.mdc` 中的 `arena runners` 一行。如果该规则或该行缺失，默认在 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 上各跑一个。这一行或交叉评审那一行里的 `auto` 或 `inherit-parent` 条目表示父模型，因此对它省略 `model` 参数。如果 Task 工具拒绝了某个配置条目，就用该家族的默认值跑这个席位，并说明情况。家族按前缀划分：`claude-*`，以及 `grok-*` 连同 `cursor-grok-*` 和 `composer-*`。被拒绝的 `composer-*` 条目改在 `grok-4.7-xhigh-fast` 上跑。没有家族匹配时，使用 `claude-opus-5-5-xhigh`。如果它连默认值也拒绝，从报错信息里取同家族最接近的有效 slug。当竞技场覆盖多个设计方向时，多派几个 runner。当工作受生成能力限制而非判断力敏感时，用同一个模型跑 N 次。按 **poteto-mode** 技能的 Subagents 一节，为每个子代理选择合适的推理等级和快速或标准速度。
4. 按 **separate-before-serializing-shared-state** 原则技能，给每个候选者自己的输出位置（能用 git worktree 就用 worktree，否则用 `/tmp/arena-<slug>/candidate-<n>/`）。

## 阶段 B：扇出

在一条消息里派出全部 N 个子代理，带 `run_in_background: true`，每个都带上任务、共享摸底材料的路径、自己的输出路径，以及指示：产出该产物，并附一份简短说明，列出它考虑过的备选方案和否决掉的东西。

如果某个候选者没有产出，用 N-1 继续，并记录这次掉队。

## 阶段 C：交叉评审

所有阶段 B 候选者完成后，从 `~/.cursor/rules/pstack-models.mdc` 的 `arena cross-judge pool` 一行中选一个模型。如果该规则或该行缺失，从 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 中选。优先选与父模型不同家族的模型。在该模型上派一个只读评审子代理。它通过路径标签看到评分量规和各候选产物，逐条标准打分，并推荐一个基底及理由。它与你在阶段 D 的阅读并行进行。候选者还在写的时候不要派它。

## 阶段 D：选定基底

挑选之前，把每个候选产物从头到尾读完。对照量规逐条打分，而不是凭整体感觉，并与交叉评审的结果比较。对基底意见一致，就确认了这个选择。意见不一致，说明你俩之中有一个存在偏见，或者量规有歧义。决定之前把两份理由都读一遍。

选出未来维护者最容易在不破坏不变量的前提下扩展的基底。两者难分高下时，按懒惰协议（Laziness Protocol），优先选边界更干净或 API 更小的那个。

## 阶段 E：嫁接

把每个落选候选产物再过一遍，找值得移植进基底的东西——通常每个候选一两样，而不是大半。按 **redesign-from-first-principles** 原则技能，手工把每处嫁接折进去，让结果在同一个心智模型下保持连贯。不要机械地粘贴。

如果各候选收敛到同一个形状，那是很强的一致信号。记录下来，直接交付这个共识形状，不需要嫁接。如果它们剧烈分叉，说明阶段 A 的规格不够。重新出题并重跑，而不是把分叉平均掉。

## 阶段 F：验证

按 **prove-it-works** 原则技能，像验证任何其他产出一样验证综合后的产物。如果验证发现了竞技场漏掉的问题，要么阶段 A 出错了（重新出题并重跑），要么某个候选者抓到了它而你漏掉了那次嫁接（回到阶段 E）。不要把它糊弄过去。

## 输出

一份综合后的产物，附一份简短的综合说明，内容包括：选了哪个基底及原因、交叉评审的结论、每处嫁接及其来源候选、否决了什么及原因、任何收敛或掉队情况，以及验证结果。
