# Linear 工单

## 这个信息源包含什么

- 描述功能、bug 及其动机的 issue
- 附加在 issue 上的项目文档（通常是 PRD 或规格说明）
- 父子 issue 关系（更宏观的专项 → 具体工单）
- issue 上的评论（澄清、范围变更、“我们为什么要做这个”的动机）
- 标签（例如 `compliance`、`customer-request`、`perf`），标出动机的类型
- 解释范围变更的状态更新
- 附件和关联的 GitHub PR

产品/业务背景往往存在于 Linear：“我们做这个是因为客户 X 提了要求”，或者“这是 Q3 合规专项的一部分”这一层。

## 如何搜索

使用 Linear MCP。

1. **从关联工单开始。** 如果种子提交或 PR 引用了工单 ID（例如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 拉取这些工单。读完整的 issue，包括评论。
2. **按关键词列出相关 issue。** 用 `list_issues` 做文本搜索：功能名、关键符号或业务术语。多试几种措辞。
3. **沿 issue 树往上走。** 如果你落在一个子 issue 上，拉取它的父 issue。子 issue 是战术层面的；“为什么”往往在父级。
4. **读项目文档。** 如果 issue 属于某个项目，用 `get_project` 并查看附加文档。规格和动机最常记录在项目级文档里。
5. **检查标签和里程碑。** 标签提示动机的类别（customer-request、incident-followup、compliance）。里程碑把工作与截止日期绑定，而截止日期常常揭示动机。

## 这里什么样的证据算好证据

- issue 描述陈述了业务问题：“客户 Acme 需要 X，因为他们要过 SOC2 审计”
- 评论记录了一个决定：“我们决定采用方案 B，因为方案 A 需要动计费服务”
- 标题像个专项的父 issue：“Q3 Enterprise Readiness” 或 “Reduce Payment Failures”
- 附加的 PRD 或规格说明
- 诸如 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 的标签

## 常见陷阱

- **范围漂移。** PR 引用的工单可能被关闭后换了个范围又重新打开。读完整历史。
- **机械式模板。** 有些团队要求填 “Why” 栏，但填的都是套话。泛泛的文字（“改善用户体验”）多半不是真正的答案。
- **过时的工单。** 旧工单往往反映的是已经变过的计划版本。核对日期，并与代码的发布日期交叉验证。
- **重复工单链。** 沿 duplicate-of 关系一路追溯到主工单。
- **私有工作区内容。** 如果你无法访问某个 issue，把它记为缺口，而不是靠猜。

## 应该返回什么

对每个相关工单：
- 工单 ID 和标题
- 从描述或评论中逐字引用的问题/动机（不要转述。综合者需要原文来引用）
- 标签、父 issue、所属项目
- 作者、创建日期、关闭日期
- 工单链接（如有）
