# Notion 文档

## 这个信息源包含什么

- PRD（产品需求文档）
- 技术规格与 RFC
- 架构决策记录（ADR）
- 设计评审的会议纪要
- 带有领域背景的团队页面
- 事故复盘
- 可能解释防御性代码的运维手册（runbook）
- 设定优先级的战略文档

“为什么”往往先以长文形式存在于 Notion，然后才变成代码。一个重要功能通常会有一篇文档。

## 如何搜索

使用 Notion MCP。

1. **用 `notion-search` 做关键词搜索。** 试试：
   - 功能名
   - 目标代码中的关键符号 / 类名
   - 作者的账号名（设计文档常常先于代码落地）
   - 错误字符串或面向用户的术语
   - 如果知道代码发布的时间，做限定时间的查询
2. **用 `notion-fetch` 拉取候选页面。** 读完整内容，不要只看预览。动机常常埋在文档中部。
3. **沿反向链接和子页面跟进。** 设计文档常有子页面，记录考虑过的替代方案、附录或实现笔记。
4. **检查相关数据库。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 可能挖到讨论过该决策的会议纪要。
5. **搜索作者的个人空间。** 如果 PR 作者有个人笔记本（在某些公司很常见），里面可能有先于代码的探索性思考。

## 这里什么样的证据算好证据

- 带有与目标代码用途吻合的 “Problem statement” 或 “Motivation” 章节的 PRD
- “Alternatives considered” 或 “Rejected approaches” 章节
- 点名目标代码是某次具体事故的修复手段的复盘文档
- 记录了“因为 Y 所以我们决定 X”、且与 PR 的作者/日期范围对得上的会议纪要
- 非敷衍填写的 ADR 模板（status、context、decision、consequences）

## 常见陷阱

- **过时的文档。** 规格常在实现之前写好且不再更新。文档描述的可能是一个已经变过的计划。与实际 PR 交叉核对。
- **文档与现实的漂移。** 规格可能写“我们要做 X”，但代码实际做的是 Y。把这种分歧标出来。综合者会把矛盾摆上台面。
- **套话模板。** 有些组织要求有 “Why” 章节，但填的都是空话。要找具体的细节。
- **没有链接的文档。** 最相关的文档可能没有任何地方链接到它。宽泛的关键词搜索有帮助。
- **多个草稿。** 如果一个主题有多篇文档，找到最终定稿或最近更新的那篇。核对日期。
- **访问受限的页面。** 如果无法访问某个页面，记为缺口。

## 应该返回什么

对每篇相关文档：
- 标题和 URL
- 作者和最后更新日期
- 动机文本（逐字引用），并注明页面/章节位置
- 相关的链接页面（便于综合者引用）
- 文档是定稿还是草稿
