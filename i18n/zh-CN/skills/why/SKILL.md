# Why

调查代码背后的动机与意图。配套的 `how` 技能回答代码做了什么、是如何工作的；`why` 回答是什么力量把它塑造成了现在的样子。

下面每次派生（spawn）都会指明 `pstack-models.mdc` 规则中的某条角色行以及一个默认值。把 `model` 设为该行的值；若规则或该行缺失，就使用默认值。当值为 `auto` 或 `inherit-parent` 时，不要设置 `model`。如果 Task 工具拒绝某个 slug，改用默认值并说明情况。如果连默认值也被拒绝，就从它的报错信息中选取同系列最接近的有效 slug。按照 **poteto-mode** 技能中 Subagents 一节的说明，为每个子代理选择适合这项任务的推理档位，以及快速或标准速度。

每次派生都是 `generalPurpose` 且 `readonly: false`（agent 模式）。**不要使用 readonly/Ask 模式。** 它会剥除 MCP 访问权限，导致基于 MCP 的调查员全部失效，综合者的引用抽查也会失效。调查员仍然不应写入任何内容。

## 操作姿态

以**细致、谨慎、精确的调查员**身份行事。对自己确切知道什么、又在推断什么保持诚实。阅读 `references/epistemics.md`，获取完整的置信度框架和措辞指南。综合者必须遵循它。

## 第 1 步. 理解目标与问题

**目标**通常是一段代码、一个模式、一个功能，或一个有名字的设计决策。**问题**通常是设计理由、一项权衡、催生它的边缘场景、一个外部约束、死代码，或一次大范围的历史梳理。

如果目标含糊（比如只说「我们为什么这么做？」却没有明确的所指），根据对话上下文（打开的文件、最近的编辑、光标位置、刚刚讨论的内容）做出最合理的猜测。简要说明你的理解，方便用户在跑偏时纠正方向，然后继续。

## 第 2 步. 建立代码锚点

在派生调查员之前，先内联构建种子上下文：文件路径与行范围、关键符号（函数、类、常量）、最近触及目标的几笔提交、从合并提交中提取的 PR 编号（主题行中的 `(#1234)` 模式），以及任何关联的工单 ID。用 `git blame -L <start>,<end> <file>` 查最后触碰该处的提交，用 `git log --follow -p -- <file>` 查看跨重命名的完整历史及补丁，用 `git log --oneline -20 -- <file>` 查看近期提交并露出 PR 编号，用 `git log -1 --format=%B <commit>` 提取 PR 编号。然后对任何有实质内容的提交，拉取 PR 正文与讨论：`gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`。这份锚点要发给每一位调查员，也要发给综合者。

## 第 3 步. 并行派生调查员

**默认进行完整的并行调查。** 目标是画出一张完整的覆盖图，而不是最小覆盖。把空结果记录下来，而不是跳过搜索。

### 发现（Discovery）

派生调查员之前，先从 Cursor 环境列出可用的 MCP。有可用工具清单时优先使用清单；否则检查 Cursor 为已启用 MCP 服务器暴露的 `mcps/` 目录。

把每个可用的 MCP 映射到一个证据类别：

1. 源代码管理历史
2. 工单 / 任务跟踪
3. 长文档
4. 团队实时聊天
5. 基础设施可观测性
6. 错误 / 异常跟踪
7. 产品分析数仓

源代码管理通过 git 和 `gh` 始终可用。对其余六类，根据 MCP 名称、服务器说明、工具名和资源描述符进行分类。如果一个 MCP 可以归属多个类别，选择与它主要证据最匹配的那个。把模棱两可的情况记录在覆盖图中。

每个有匹配 MCP 的类别各派生一名调查员，全部放在同一条消息里以并发运行，每名调查员恰好只负责一个工具或 MCP。不要让一个代理同时覆盖多个 MCP。`model`：取 `why investigators` 那一行的值，默认 `grok-4.7-xhigh-fast`。

每位调查员的提示词 = 填写好的 `references/investigator-prompt.md`，另加：
- 所选 MCP 对应的类别行动手册 `references/sources/<source>.md`，改写自 `references/source-playbook.md` 中的示例
- `references/sources/incident-postmortem.md`（**如果目标代码看起来是防御性的**：null 检查、重试逻辑、超时处理、限流、功能开关、出口流量防护、OOM 处理器）
- 代码锚点和用户的原始问题

### 调查员名册，每个可用证据类别一名

下面每个类别都独一无二地擅长揭示某一种形态的「为什么」，标注在「最擅长」之后。用它来预判能拿回什么、在某类查无结果时为这个缺口命名，并且——仅在有证据表明完全无关的极少数情况下——为跳过提供理由。

1. **源代码管理**（git 历史、`gh` 查 PR、代码注释、测试）。始终派生，这是唯一有保证的来源。最擅长*评审过程中沉淀下来的实现期理由*。
2. **工单 / 任务跟踪**（如 Linear、Jira、GitHub Issues、Plane、Shortcut MCP）。最擅长*产品或业务层面的驱动力*。当「为什么」的答案在工程之外时最强。
3. **长文档**（如 Notion、Confluence、Google Docs、Coda MCP）。最擅长*成文的长篇设计理由*——在变成代码之前就已写就。
4. **团队实时聊天**（如 Slack、Discord、Microsoft Teams、Mattermost MCP）。最擅长*从未落到文档里的实时讨论*。当源代码、工单、文档的纸面记录都很稀薄时尤为重要。
5. **基础设施可观测性**（如 Datadog、New Relic、Honeycomb、Grafana、Splunk MCP）。最擅长*催生代码的基础设施与运行时现实*。当目标是在响应基础设施信号（超时、重试、限流、熔断）时最强。
6. **错误 / 异常跟踪**（如 Sentry、Rollbar、Bugsnag、Airbrake MCP）。最擅长*催生防御性或纠正性代码的具体异常与错误轨迹*。对 catch 块、null 防护、类型检查、重试及其他防御手段最强。
7. **产品分析数仓**（如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift MCP）。最擅长*塑造代码的产品与数据现实*。对开关门控的代码、实验驱动的发布、数据迁移，以及「这个数字是哪儿来的」这类问题最强。

### 什么时候可以跳过某位调查员

只有给出**明确、书面的理由**时才可以，且该理由要写入最终的 Sources Consulted（已查阅来源）。正当的理由只有两条：

- **该类别在此环境中没有可用的 MCP**。把它标记为缺口，而不是一种选择：「已跳过团队实时聊天。没有匹配的 MCP 可用，因此对话记录无法检索。」
- **该来源被证明确实无关**，而不只是「可能无关」。门槛很高：「已跳过错误 / 异常跟踪。目标是一个构建期脚本，没有运行时代码路径。」

如果你的范围评估认为目标是单笔提交的琐碎改动、且 PR 描述已经包含完整答案，那么**只有在**确认全部七个可用类别的搜索都会冗余之后，才可以直接内联回答。并明确说明这一点。这种情况应该很罕见。

## 第 4 步. 综合

派生一名综合者。`model`：取 `why synthesizer` 那一行的值，默认 `claude-opus-5-5-xhigh`。它会收到：
1. 调查员的发现，包括所有空结果，以及所有附理由的跳过类别
2. 代码锚点
3. 用户的原始问题
4. `references/epistemics.md` 中的认识论框架
5. `references/synthesizer-prompt.md` 中的综合者提示词模板

## 第 5 步. 呈现

把综合者的产出呈现给用户。你可以为清晰起见做轻度编辑，或补充对话中的上下文，但**不得改写置信度措辞**。

## 输出格式

结构以 `references/synthesizer-prompt.md` 为准：The Question（问题）、The Code in Question（相关代码）、What We Found（我们查到的）、What We Can Reasonably Infer（可以合理推断的）、Competing Hypotheses（相互竞争的假设）、What We Don't Know（我们不知道的）、Sources Consulted（已查阅来源）、Confidence Summary（置信度摘要）。可按需调整，但置信度的分层必须保持原样，且 Sources Consulted 保持每位调查员一行——包括查无结果或被跳过的调查员——并注明原因。

在 Sources Consulted 之后，如果用户的 `why` 问题是改动这段代码的前奏，就把溯源发现转化为一份 Preserve（保留）/ Change（改动）/ Avoid（避免）/ Risk（风险）约束集，用于规划这次改动。

## 需要避免的常见失败模式

- **近因偏差**。以为最近的提交就是权威答案。当前的形态往往是许多早期决策层层累积的结果。往回追溯。
