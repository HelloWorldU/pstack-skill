# 验证已有的修复

当一个打开的 PR 或已合并的提交很可能修复了所报告的问题时，使用本模式。

已有的产物拥有这个修复。验证它。不要编辑它、不要编写与之竞争的补丁、也不要再开另一个 PR。

## 鉴定产物

要求一个具体的产物：

- 一个打开的 PR，其代码改动针对该症状
- 一个已合并的 PR
- 一个已合并的提交，代码和意图都匹配

没有 PR 或提交支撑的帖子说法、跟踪器状态、分支名或病因假设都不算数。

当存在多个产物时，选择源帖子或跟踪器里链接的那个。否则选择与被影响代码最接近的那个，并说明原因。

## 保护工作区

当仓库支持时，使用隔离的 worktree 或另一个干净的检出。不要覆盖用户的改动。

记录：

- 基线版本
- 打补丁的版本
- PR 或提交的 URL
- 两次运行共享的构建和环境输入

使用常规的 `github.com` PR 链接。

## 测量基线

对于一个打开的 PR，用它的基分支作为基线。

对于已合并的修复，当修复前一个版本能够构建且代表旧行为时，用紧邻修复之前的那个版本。

通过配置好的控制适配器：

1. 启动基线应用。
2. 确认应用和环境正确。
3. 通过真实 UI 操作走一遍被报告的路径。
4. 观察有区分度的症状。
5. 重置并重复。
6. 截取基线录制、截图和状态检查。

如果症状在基线上没有出现两次，就没有基线。不要声称修复有效。

## 测量打补丁的构建

用相同的环境和数据构建并运行该 PR 或修复提交。

1. 走同样的 UI 路径。
2. 重复两次。
3. 确认损坏的状态已经消失。
4. 确认预期的状态出现。
5. 截取修复后的录制、截图和同样的状态检查。

不要止步于编译或测试通过。修复后的结果必须来自一个运行中的打补丁应用。

## 结果

### 已确认

基线复现两次，打补丁的构建两次都解决了它。

- 把运营状态标记为已验证。
- 链接该产物。
- 在源预检之后，在源帖子里发一条简洁的回复。
- 附上前后对照结果。
- 不开任何 PR。

### 修复不足

症状在基线和打补丁的构建上都出现。

- 把运营状态标记为已复现但未修复。
- 链接该产物，并说明它没有解决该症状。
- 如果本次运行还没有发过「已确认复现」的源更新，就把它发出去。
- 不开任何竞争性的 PR。

### 无法定论

基线无法复现、打补丁的应用跑不起来，或者证据没有展示有区分度的状态。

- 不要声称成功。
- 说明哪一半无法测量。
- 把结果留在运营帖子或运行输出里。
- 除非有直接的问题必须回答，否则不在源帖子里发任何内容。

## 清理

停止两个构建，按保留策略移除临时配置文件和截取产物，并把仓库恢复到之前的状态，且不丢弃用户的工作成果。
