# 复现并修复问题

等待来源线程中出现可信的分诊标记。通过目标应用的真实 UI 复现确切的症状。当已有修复存在时验证该修复。只有在确认复现之后才尝试有边界的修复。

加载由自动化提供的外部 Benny 配置。如果配置、必需的操作、控制适配器或已填写的功能地图缺失，按失败关闭处理。

## 硬性安全规则

- 在做任何工作之前，先冻结来源频道和根线程坐标。
- 绝不在来源频道发布根消息。
- 每次在来源线程发帖之前，先对来源父消息做预检。
- 协调者是唯一的 Slack 发帖者。
- 被委派的分析 worker 是只读的，只返回发现或媒体笔记。
- 修复阶段的代码 worker 只有在其环境被证明排除了 Slack 凭据和一切 Slack 写操作时才可以编辑。否则由协调者编辑。
- 每个子提示词必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 写操作。
- 绝不给子代理 Slack token、发帖指令、用于发帖的来源坐标，或对外汇报的权限。
- 如果某个子代理运行时需要 Slack 写权限，就不要启动它。
- 工具型机器人是证据来源。除非有人明确把修复委派给它们，否则它们不拥有修复权。
- 确切的判别性症状必须通过真实 UI 交互出现两次。
- 状态检查可以用于确认观察结果。它不得注入或强迫症状出现。
- 没有确认的复现，就没有自创的修复。
- 已存在的 PR 或提交会把本次运行切换为验证模式。不要在其之上另写修复。
- 使用 `github.com` 的 PR 链接。
- 让截图、录屏、日志和 token 远离版本控制。
- 委派分析时使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证中应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻结来源坐标

在列工作清单或委派之前：

1. 要求触发频道等于配置的来源频道。
2. 当 `trigger.thread_ts` 存在时，把 `SOURCE_THREAD_TS` 设为 `trigger.thread_ts`。否则使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变的值。
5. 读取来源线程，验证其根消息恰好具有这些坐标。
6. 获取来源永久链接。

绝不要用回复时间戳、运维时间戳或状态消息时间戳替换这些值。

每次在来源频道发帖之前：

1. 按不可变坐标读取线程。
2. 确认父消息存在、未被删除、且仍属于来源频道。
3. 只用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再次读取线程，验证新消息是一条回复。

如果任何一项检查失败，什么都不发。绝不在根消息或备用频道里重试。

## 2. 等待分诊契约

在配置的判定预算内观察来源线程。等待期间保持静默。

只有满足以下条件才接受判定：

- 其作者匹配 `slack.triage_identity_user_id`。
- 它是 `SOURCE_THREAD_TS` 下的一条回复。
- 它恰好包含一个配置的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只对 `bug` 或 `performance` 继续处理。捕获可选的 tracker URL。遇到 `other`、判定缺失、作者不可信、标记冲突或超时时静默停止。

这个标记取代了私有机器人身份和自由形式的判定匹配。

## 3. 应用归属与修复产物关卡

在开始工作前立即重新读取线程。

### 有人明确表示要修

当一个人明确认领修复、给出具体实现计划，或要求另一个代理去实现、打补丁、修复或开 PR 时，停止。

不要把以下情况当作修复归属：

- 一个机器人总结了证据。
- 一个工具查询了日志或工单。
- 有人请机器人诊断、解释、检查或复现。
- 一个机器人发布了原因假设，但没有同意去实现。

判断的是被请求的动作，而不是有没有机器人出现。

### 修复产物已经存在

如果一个打开的 PR 或已合并的提交很可能修复了这个报告，切换到 `references/verify-existing-fix.md`。

产物可以来自线程、tracker 工单、仓库历史或 PR 搜索。没有提交或 PR 佐证的声称不算修复产物。

如果有人认领了这项工作但还没有产出产物，停止。不要和他们抢跑。

## 4. 打开一个可选的运维线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流中唯一允许的根帖。

把它的坐标存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要把它们与来源坐标混淆。

使用配置的纯 Unicode 状态字符串。状态文本保持简短：

- 复现中
- 无法复现
- 受阻
- 已复现
- 正在验证已有修复
- 正在尝试有边界的修复
- 草稿 PR 已打开
- 修复未能落地

优先使用配置好的 Cursor Slack 操作。只有当用户为某个狭窄的缺失能力（例如编辑这一条状态消息）配置了 `BENNY_SLACK_BOT_TOKEN` 时才使用它。绝不把 token 暴露给 worker。

如果没有配置运维频道，把详细状态保留在自动化运行输出中。不要用来源频道根消息替代。

## 5. 加载并检查控制适配器

读取 `references/control-adapter.md` 和 `control.feature_map_path` 处已填写的功能地图，然后调用 `control.skill_name` 指定的技能。

找到与报告的用户路径相匹配的功能地图小节。在驱动应用之前先读它。如果没有小节覆盖该功能，把本次运行标记为受阻，而不是凭空发明路径或选择器。

要求全部七项能力：

1. 拉起配置的目标应用和测试环境。
2. 导航到已映射的功能并走遍其文档化的状态。
3. 用点击、输入、按键、滚动、拖拽、调整尺寸或导航来驱动真实 UI。
4. 在不改变状态的前提下检查状态。
5. 截屏。
6. 开始和停止屏幕录制。
7. 清理进程、会话、配置档和临时数据。

如果适配器缺失，或任何必需能力缺失，把运维状态标记为受阻并停止。不要把截图、单元测试、状态改动或读源码冒充成 UI 复现。

## 6. 研读报告

阅读完整的来源线程，以及存在的 tracker 工单。

收集：

- 确切的操作路径
- 预期行为
- 观察到的行为
- 两者分叉处的判别性状态
- 发生频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

查看截图和视频。在有用时，用只读的并行 worker 做代码历史、测试思路、爆炸半径映射和媒体审阅。每个 worker 只得到一个狭窄的问题，并附带 Slack 禁写令。

用 pstack 的 `how` 技能在仓库里追踪操作路径。用 `why` 查回归历史和防御性代码。形成相互竞争的原因假设，并找出能把它们区分开的证据。

## 7. 复现

通过控制适配器拉起目标应用。

动手之前确认正确的应用、工作区、账号、数据集和功能状态。使用稳定的应用标记。不要只依赖窗口顺序或眼熟的标题。

通过真实 UI 操作走报告的路径。

在宣布复现之前：

1. 说出正确的最终状态。
2. 说出损坏的最终状态。
3. 走到两者分叉的位置。
4. 观察到损坏状态。
5. 重置足够的状态，让第二次尝试相互独立。
6. 重复同一路径，再次观察到同样的损坏状态。
7. 在可能时交叉核对一个真实的状态值。

一个符合预期的对话框、加载状态或设置步骤不是 bug。要捕获能把正确行为和损坏行为区分开的最终状态。

使用配置的复现预算。如果症状没有在该预算内复现，报告干净的「无法复现」结果。如果环境无法提供某项必需能力，报告「受阻」并说明缺了什么。

## 8. 捕获并审阅证据

对成功的复现：

- 录制走完症状的完整路径。
- 截取损坏最终状态的截图。
- 保存一条简短笔记，记下确切步骤和观察到的状态。
- 把产物放在配置的临时产物目录里。

让一个只读的媒体审阅者回答一个问题：证据是否清晰可见地展示了判别性的损坏状态？

如果答案是否定或不确定，复现不算确认。捕获更好的证据，或者使用「无法复现」。

配置了运维线程时，只在运维线程里发布详细证据。来源线程的更新保持简洁。

## 9. 汇报复现结果

先更新运维状态。

对于「无法复现」或「受阻」，在来源线程里什么都不发。运维线程或运行输出承载结果。

对于确认的复现，执行来源预检，最多发布一条未被要求的来源回复：

- 说明问题已复现。
- 有运维证据线程时给出链接。
- 最多包含三条简短发现。
- 有 tracker 工单时给出链接。
- 默认不要 ping 负责人。

只有当配置的 Slack 操作能把附件保留在同一来源线程内、且组织的留存策略允许时，才附带证据。

等待配置的反驳窗口。如果有人指出设置或解读有误，纠正并复现一次。在窗口关闭且没有有效反驳之前，不要开始修复阶段。

## 10. 验证已有修复

当修复产物存在时，遵循 `references/verify-existing-fix.md`。

验证必须在基线上展示症状、在打过补丁的构建上展示症状消失。两条路径都各走两次真实 UI。

不要编辑已有修复、不要添加竞争补丁、不要开替代 PR。

## 11. 评估有边界的修复

只有同时满足以下所有条件才尝试修复：

- 结果是干净的确认复现。
- 媒体审阅确认了损坏的最终状态。
- 没有出现已有的修复产物。
- 反驳窗口内没有人认领修复。
- 运行时证据已锁定根因。
- 可能的改动符合配置的修复预算和仓库范围。
- 控制适配器能同时运行基线构建和打过补丁的构建。

如果任何条件不满足，保留复现报告并停止，不开 PR。

关卡通过时，把运维状态更新为「正在尝试有边界的修复」。

## 12. 定位根因并实现

协调者拥有每一条 Slack 发帖、最终 diff 评审、提交和 PR。

只读 worker 可以：

- 追踪代码和历史
- 提议测试
- 绘制爆炸半径
- 评审 diff
- 审阅媒体

它们不编辑、不执行外部写操作、不发状态、不拥有修复权。

在此阶段，只有当工具隔离从该 worker 环境中移除了 Slack 凭据和一切 Slack 写操作时，才可以委派一个严格限定范围的代码编辑。它的提示词仍必须带上明确的 Slack 禁写令。协调者评审这次编辑，并运行或验证所需测试。如果工具隔离不确定，把编辑留在协调者手里。

用运行时证据确认机制。编辑之前先排除相互竞争的假设。

用最小的合理改动修复根因。

- 当有便宜的本地测试目标时，调用 pstack 的 `tdd` 技能，并在修复之前先写失败测试。
- 当路径昂贵、不清晰或重度依赖集成时，说明为什么跳过 TDD。
- 不要夹带无关清理。
- 如果改动膨胀到超出配置的工作量或风险预算，停止。

## 13. 证明修复有效

保留原始的基线证据。

在打过补丁的构建上：

1. 走同样的真实 UI 路径。
2. 重复两次。
3. 展示损坏状态已经消失。
4. 展示预期状态取而代之。
5. 捕获修复后的录屏和截图。
6. 交叉核对基线时用过的同一个真实状态值。

编译通过、单元测试、代码评审或看起来合理的 diff 都不算修复后证据。

运行聚焦测试，然后围绕被改行为做爆炸半径冒烟。覆盖改动可能波及的邻近状态、输入、权限、平台和失败路径。如果仍有回归，不开 PR 直接停止。

## 14. 打开草稿 PR

只有在拿到前后对照证据之后：

- 评审最终 diff，检查无关改动和机密信息。
- 运行仓库要求的检查。
- 当仓库工作流允许时，创建小而有序的提交。
- 打开草稿 PR。绝不从这个工作流合并或部署。
- 用 tracker 支持的 PR 语法关联配置的 tracker 工单。
- 使用配置的公开 URL 形式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含复现步骤、根因、测试结果、前后证据和爆炸半径检查。
- 把 PR 文本和所有 Slack 更新过一遍 pstack 的 `unslop` 技能。

如果 PR 创建失败，不要宣称成功。把提交或分支状态保留在运行输出里，并把运维状态标记为「修复未能落地」。

成功时，把运维状态标记为「草稿 PR 已打开」，并在运维线程里发一条带 PR 链接的简洁回复。不要创建第二个来源频道根帖，也不要再发未被要求的来源回复。

## 15. 跟进与清理

在一个跟进窗口内观察配置的运维线程。

- 用已收集的证据回答直接的问题。
- 当某条具体纠正推翻了原有设置时，应用它并重跑一次复现。
- 不介入人类协调和闲聊。
- 被要求停止时就停止。

始终调用控制适配器的清理能力。产物的保留时间不得超过配置的留存策略允许的范围。
