# 分诊问题报告

对一条 Slack 报告进行分类，并在其来源讨论串中发布一条有用的结论。只为明确的新 bug 创建跟踪工单。不要在这里复现或修复它。

加载自动化提供的外部 Benny 配置。如果配置缺失、格式错误或不完整，立即停止，不发布任何消息，也不写入工单跟踪系统。

## 硬性安全规则

- 来源频道和根讨论串坐标不可变。
- 绝不在来源频道发布根消息。
- 绝不向其他频道发帖、广播回复、发送私信，或另起一个替代讨论串。
- 在任何跟踪系统写入之前、以及发布结论之前，立即对来源父消息做预检。
- 如果父消息缺失、已删除、不可访问或不确定，立即停止，不做任何写入。
- 只发布一条实质性结论。不要播报进度。
- 协调者是唯一的 Slack 发帖者。
- 被委派的工作者只返回发现。它们必须是只读的，不获得任何 Slack 凭据或写操作权限。
- 每个子提示词都必须禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 写操作。
- 如果工作者隔离无法强制执行这些限制，就在协调者内部完成这项工作。
- 绝不创建无法链接回来源讨论串的工单。
- 宁可不建工单，也不要凭猜测建单或建出重复工单。
- 对来源坐标应用 pstack 的 `principle-separate-before-serializing-shared-state` 原则。
- 对最终结论应用 pstack 的 `principle-minimize-reader-load` 原则和 `unslop` 技能。

## 1. 冻结来源坐标

在制定工作清单或委派之前：

1. 从触发器中读取 `source_channel_id`。
2. 要求它等于配置的来源频道。
3. 当 `trigger.thread_ts` 存在时，将 `SOURCE_THREAD_TS` 设为它的值。否则使用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 将 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存储为不可变值。
6. 读取该讨论串，验证其根消息恰好具有这些坐标。
7. 获取一个稳定的来源永久链接。

之后每一次读取来源和发帖都必须使用这些存储值。绝不用回复时间戳或运营讨论串时间戳替换它们。

## 2. 通读整份报告

在做决定之前，读取根消息和当前所有回复。

捕获：

- 报告者的原话
- 产品版本、应用构建、环境和平台（如有）
- 期望行为
- 实际观察到的行为
- 频率与触发条件
- 错误文本或堆栈特征
- 已有的工单、提交或 PR 链接
- 任何明确说明已有人在修复它的陈述

检查每一个相关附件。

- 以充分的有效分辨率读取截图。
- 审看视频，找出区分正常行为与异常行为的状态转变。
- 读取日志、追踪和崩溃文本，寻找具体特征。
- 如果媒体内容需要专家审阅，使用只读的媒体工作者并提出一个聚焦的问题。该工作者只返回发现。
- 如果某个附件无法读取，在结论中说明。不要编造它展示了什么。

在向报告者索要更多信息之前，先利用讨论串中已有的证据。

## 3. 路由之前先追溯原因

在选择负责人或目的地之前，做一轮有边界的源码和历史排查。使用 pstack 的 `how` 技能，追溯从被报告操作到观察结果的路径。当报告看起来像回归或涉及防御性代码时，使用 `why`。

1. 识别从被报告操作到观察结果的可能代码路径。
2. 检查可见症状属于该代码路径，还是属于它下面的某个依赖。
3. 当报告看起来像回归时，检查近期变更。
4. 检查是否已有合并的提交或打开的 PR 在处理同一症状。
5. 将已确认的事实与假设分开。

这轮排查不需要得出完整的根本原因。它必须足够有力，以避免把可见症状路由给错误的负责人。

如果无法读取仓库，不要猜测代码负责人。继续给出保守的分类，并说明原因追溯不可用。

## 4. 分类

选择一个类别。

### Bug

某处违背了预期行为。例子包括错误输出、状态损坏、报错、崩溃、挂起、静默无操作或回归。

### 性能

报告描述了可测量的变慢、内存占用过多、耗电、卡顿或其他资源问题。把它当作 bug 处理，但保留测量数据和性能剖析结果。

### 功能请求

当前行为看起来是有意为之，而报告者想要一种不同的行为或操作方式。

### 问题或反馈

报告是在询问某功能如何工作、表达一个没有具体缺陷的偏好，或给出一般性反馈。

### 改派

原因追溯表明，另一个已配置的目的地才是该问题的归属方。

当 bug 与功能请求的界线不清时，不要建档。这一条结论可以提出一个聚焦的问题，并使用 `other` 标记。

## 5. 应用已配置的路由

从 `routing.map_path` 读取可选的路由映射。

- 按已确认的产品区域、代码路径或错误特征匹配。
- 当原因追溯指向别处时，仅有可见症状是不够的。
- 如果没有路由匹配，说明负责人不明确。不要猜测。
- 不要跨频道转发。在来源讨论串里告诉报告者该把问题带去哪里。

默认不 @ 负责人。只有同时满足以下所有条件时才允许 @：

1. 路由映射明确点名了该负责人。
2. 配置允许这种类型的 @。
3. 该条目是需要负责人意见的功能请求，或近期历史以强证据指出了可能的回归引入者。
4. 该负责人不是一个宽泛的值班组。

其他情况一律不 @。

## 6. 使用工单跟踪适配器

跟踪系统是一个适配器，不是必需的供应商。Linear 适配器是一个有效示例。GitHub Issues 适配器或其他跟踪系统也可以实现同一契约。

已配置的适配器必须提供：

- 按文本、状态、标签、来源 URL 和日期范围搜索工单
- 读取单个工单及其链接
- 创建带标题、正文、状态、标签和来源 URL 的工单
- 更新已有工单而不替换无关字段
- 添加来源链接和复发备注
- 如果 Slack 交接失败，取消、关闭或删除本次运行创建的工单

如果某个必需操作不可用，该写入以失败即关闭处理。

在运行时解析配置的团队、项目、状态和标签。不要编造 ID、创建标签、指派负责人或设置优先级，除非配置明确要求。

## 7. 去重

始终检查该来源永久链接是否已经关联到某个跟踪工单或之前的分诊回复。如果是，不要重复发布或创建。

对于 bug 和性能报告，使用以下条件搜索跟踪系统：

- 确切的错误或崩溃特征
- 产品区域
- 触发条件
- 症状
- 版本或日期窗口
- 疑似引入回归的提交
- 来源永久链接

选择一种结论：

- 确信重复：特征相同，或区域、触发条件和症状相同，或已确认存在共同原因。
- 可能相关：存在共同原因是合理的，但未被证实。
- 相似度弱：相似只是表面的。
- 无匹配。

对于确信重复，用来源永久链接和一条简短的复发备注更新已有工单。除非配置要求，否则不要重新打开、改标签或重新指派它。

对于可能匹配，在结论中以不确定的方式链接它，不创建任何内容。

一个早已关闭的工单是一条回归线索，并不自动等同于仍然存在的重复。

## 8. 决定是否创建

只有以下所有条件同时成立才创建：

1. 分类是 bug 或性能。
2. 行为明显已损坏。
3. 问题仍然存在，或未确认已被修复。
4. 去重未发现确信的或合理的现存匹配。
5. 来源父消息和永久链接通过了预检。
6. 跟踪系统的目标字段已解析完成。
7. 如果结论发布失败，适配器能够进行补偿。

绝不为功能请求、问题、反馈、改派、可能重复、确信重复或已修复的问题创建工单。

新工单必须自包含：

- 平实的标题，指明区域和症状
- 报告者原话引用
- 期望行为与实际行为
- 版本和环境，或 `unknown`
- 触发条件与频率
- 来源讨论串永久链接
- 简短的原因追溯发现，假设要标注为假设
- 支持时内联截图或代表性视频帧
- 其余证据材料的链接
- 配置的接收状态和标签

不要把猜测的根本原因写进标题。

## 9. 发布一条结论

重新对来源父消息做一次预检。然后以 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 恰好发布一条回复。

绝不在 `thread_ts` 为空的情况下调用来源频道的发帖操作。

保持回复简短：

- 以结论开头。
- 有工单时，链接已有的或新建的跟踪工单。
- 必要时提及改派或一个缺失的事实。
- 最多包含一个被允许的负责人 @。
- 以恰好一行标记结束。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只使用已配置的标记字符串。复现自动化只有当标记来自该来源讨论串中已配置的分诊身份时才会信任它。

发布后，读取同一来源讨论串，验证结论出现在 `SOURCE_THREAD_TS` 之下。如果没有，绝不要在根消息处重试。

如果本次运行创建了跟踪工单而结论没有落地，使用适配器的补偿操作。验证该工单已被取消、关闭或删除。如果补偿无法验证，只在自动化运行输出中报告该失败。

## 10. 观察一个跟进窗口

在配置的跟进窗口内观察来源讨论串，然后停止。

- 只回答直接向分诊身份提出的问题。
- 在安全时，对跟踪工单应用具体的更正。
- 不要在同一次运行中发出第二个标记。
- 不参与人类协调和旁支闲聊。
- 如果有人要求自动化停止，提前停止。

不要不止一次延长窗口。新报告应当启动一次新的运行。
